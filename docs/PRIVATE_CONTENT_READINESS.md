# 私有内容就绪检查与升级顺序

公开 `/api/health/content` 仍是 204 空响应，只证明处理程序存活。维护候选使用独立 `POST /api/internal/content-readiness`，在清理前和清理后分别证明网站能通过当前受限 reader 读取预期批次的一条已公开 Status 正文。本项只准备源码和离线验收，不安装密钥、运行包或恢复任务。

## 协议与防护

网站 `CONTENT_READINESS_SECRET` 留空或不是 64 位小写十六进制时，入口关闭。维护的 owner-only 环境文件使用独立 `RETENTION_READINESS_SECRET`；两端同值，独立于 purge、媒体、Notion 和数据库凭据。通过 Authorization Bearer 头发送，不进入 URL、窗口 JSON、日志、Git 或浏览器。真实生成、保存、云端配置、轮换及撤销另行授权。

请求包含固定格式 `private-content-readiness-v1`、预期 `runId`、每次新生成的 32 字节随机 `nonce`，以及 `{id,slug}` 的 Status 样本。样本必须从同一批已验收的完整来源／访客回执中选取，真实值只进私有配置。服务器在验证密钥及至多 1 KiB 请求体后，要求 database v2、published 和可验证 TLS 配置；不触发 Notion 或对象读取。

通过运行时的原网站 repository 直接读取：先取空选择的发布版本，读取指定 Status 正文，再取发布版本。两次版本必须一致且属于预期 run；样本身份必须匹配，正文必须完整。失败、样本撤回、空结果、切换批次、provider 不符、权限隔离失败、取消或超限都返回空错误，原始错误不外传。此证明只覆盖该样本和原 reader 路径，不代替全内容完整性、媒体、区域网络或浏览器验收。

成功仅返回格式、ready、预期 run 与本次 nonce；浏览器和两个 CDN 缓存头均 no-store。维护客户端严格验证字段、run 和 nonce，拒绝缓存、重定向、旧公开健康协议、额外字段及超过 4 KiB 的响应；没有回退或自动重试。随机挑战用于拒绝陈旧／缓存的成功响应，不是服务端保存的一次性授权票据。一个持有密钥的客户端可以发起新检查，密钥必须受保护。

每个 warm instance 同时只接纳一项私有检查。处理程序收到取消信号时及时返回，仍在排空的工作继续占用该实例准入，不能立即再发一轮；这不是跨实例全局限流。实际部署是否传递客户端断连取决于平台配置，本项未启用该配置；独立 8 秒期限仍适用。

## 配置与成本边界

维护新配置格式是 `retention-daily-config-v3`，新窗口是 `retention-daily-window-v3`；旧 v2 明确拒绝，不自动改写。配置用 `readinessURL` 和 `readinessSample` 取代 `healthURL`；目标必须是 HTTPS、精确私有路径且无用户信息、查询或片段。窗口固定相同批次、样本、原锁、成功证明和程序摘要；不保存密钥。调度 `--check` 仍只检查本机配置／状态／程序，不读取环境凭据、不请求网站。

每轮最多两次私有 POST，每次客户端 10 秒、4 KiB 应用响应；服务器从请求开始至多 8 秒、8 次 SQL、256 KiB 的 `JSON.stringify(rows)` 累计逻辑响应。两次分别需要至多 16 次 SQL、512 KiB 逻辑行响应、8 KiB 客户端响应及 2 KiB 请求体预算。首次权限／能力检查也在 SQL 预算中；缓存命中的旧内容不能作为证明。没有读取正文外的媒体文件。

SQL 行字节在驱动返回后计算，首个超限结果已被接收；不宣称严格限制协议字节、服务端计算、首次超限结果或云平台账单。预算超限后拒绝进一步 SQL，也不把预算重置后重试。维护本身的数据库、归档／恢复及 HTTP/TLS 费用另算；实际安装／运行窗口须统一包含全部操作、停止与未知结果核账，不因代码内有预算而免除授权。

## 可审阅的升级顺序

1. 先按单独授权核对来源同步与 retention 的暂停状态、原锁和未知操作；保存原运行包、配置、日志和回执。先解决当前未知提交及源同步失败，不分配新运行或删除待处理事件。本记录没有刷新这些真实状态。
2. 在独立候选目录固定网站提交、Node 24、两份锁文件／完整依赖、同步访客包、维护 v3 包及全部依赖文件摘要。维护清单必须包含新 readiness 模块、协议模块和它们的递归运行依赖；不能只固定旧 CLI。用虚构窗口演练前置失败、后置失败、超限、取消和成功；本机 `scheduled-cli --check` 不代表真实就绪。
3. 准备两端专用密钥的私有配置前后像和撤销方案，向用户申请一次覆盖云端配置、安装、必要身份／状态检查、预／后探测及预计流量的明确授权。真实值不写入本文件。另满足 B03 网站 reader 隔离安装验收等发布前置条件。
4. 在保持业务任务停止的窗口内，先安装受审的同步访客包及维护 v3 包，固定配置，但保持不运行。随后按独立发布授权发布网站并配置同一专用密钥；公开 204 与同步访客步骤必须同时兼容。旧同步包不得继续以 200/provider 字段判定成功。旧维护包不得在新站点上运行，因为它只在删除后检查健康。
5. 按授权以同一预期批次／样本执行有界私有检查；只有网站、包身份、前置数据库隔离、完整同批成功证明、暂停／锁条件、预算及回退全部满足，才可另行批准恢复。私有就绪检查本身不自动恢复来源、维护、调度或发布。
6. 回退时先停业务并排空／核账在途操作，再按受审前后像恢复网站与匹配的同步／维护运行包。若撤销密钥或缺失私有证明，新维护包保持拒绝，不为恢复清理退回公开 200。保留失败与未知结果，不自动重试删除。

本顺序是待审安装方案，不是已执行回执。当前源码具备私有证明和兼容流程，实际环境是否满足条件仍须授权后验证。
