# 后端性能复查与后续优化顺序

受审版本：develop `8cbc7c5978400e14baf53bf4e61394e7afb2454c`；同期 main 为 `df449688283503b421a6803faafc72dbc25bece7`。这是 427 scoped 读取、430 社交封面 SQL 优化及后续作品筛选后的第二轮复查，不把这些已经完成的工作重复列为待修复。

本轮完成源码审查与三个离线原型对比，没有修改应用代码、SQL、依赖、契约、fixtures 或运行配置。所有数据均为虚构数据，SQL executor 为显式模拟；没有生产 SQL、页面、图片或 Notion 请求，没有改同步、清理或部署。已有同步恢复、快照保留、F21 与 F28 小图工作由各自现有任务推进。

## 建议的实施顺序

| 顺序 | 已定位的问题 | 方案与收益边界 |
| --- | --- | --- |
| 1 | metadata 在途登记只按 kind 保存一项，请求交错会覆盖彼此的登记 | 按请求作用域再按 kind 分组；只共享同一作用域仍在进行的读取，结束或失败即清理。原型把两个请求交错的 3 次读取降至应有的 2 次，不跨请求缓存结果。 |
| 2 | 内容时间线在排序比较中反复构造 Intl 日期格式化器、反复计算同一条目的日期 | 每次操作创建一个格式化器，按事件预计算日历日，再用已有排序规则比较。保留纯日期、无日期、时区、同日精度及 ID 决胜规则。 |
| 3 | 社交封面虽然已改善 SQL 计划，仍在平台筛选与分页前装饰整个快照 | 先读取当前合格作品与排序身份，选出当前页，再批量查询这页封面。首页先混排选页，作品页先筛选／排序选页，二者各自保留原游标。 |
| 4 | 每次搜索仍从全部合格正文抽取文字片段，再在应用扫描匹配 | 先比较同步时生成带依赖的文字片段与现有即时抽取；再评估索引候选过滤。不要直接缓存已经过资格过滤的搜索结果。 |
| 5 | SQL 传输、资格投影、分页、搜索和排序相互耦合，慢请求的阶段观测不完整 | 逐项抽出有类型的读取能力与纯投影／排序函数，沿现有 detail 计时扩展到列表、搜索、时间线；先做可观测、可对比的边界，避免只移动文件。 |

## 1. 并发去重有交错失效，内容隔离本身未失效

位置：`src/server/database/website-repository.ts` 的 `metadataPending` 与 `metadata()`。

当前只保留 `Map<kind, {context, work}>`：A 请求启动 movie 元资料读取，B 请求启动同类读取会替换 A 登记；A 接着需要同类年份时，虽然 A 原来的 SQL 尚未结束，仍会再发起一次。context 校验防止错用另一请求的结果，因此这是重复 IO 问题，不是已证明的数据串用。

原型使用 `WeakMap<requestContext, Map<kind, Promise>>`，保留无作用域时独立读取、成功及失败后的清理和对外副本。确定性的 A／B／A 交错中，当前实现调用 3 次，原型 2 次，返回的列表与年份完整相同。没有用定时器竞速证明该结论。

实施还应验证取消、失败后重试、无作用域、不同 kind、几十个作用域交错及已完成结果不复用；本次原型尚不代替这些回归。

## 2. 日期计算应从排序比较移到每轮准备阶段

位置：`src/lib/content/website.ts` 的 `dayOf()`／`timelineEvents()`；对照 `home-feed-core.ts` 已有每轮格式化器与 moments Map。旧时间线排序还被首页混排前调用，随后首页会再排序一次；后续可把“生成事件”和“按独立时间线排序”分开，减少首页的重复排序，但先保留相同选择和游标规则。

Node 24.21.0，同进程、预热后交替执行五轮，单位为毫秒中位数；输入为日期、datetime 和 null 混合的虚构影视记录。对三个时区 UTC、Australia/Melbourne、Asia/Shanghai 比较完整事件 DTO，均相同。

| 条目数 | 当前实现 | 每轮仅复用格式化器 | 复用格式化器并记住各日期结果 |
| --- | ---: | ---: | ---: |
| 250 | 59.139 | 9.701 | 0.456 |
| 1,000 | 305.300 | 37.851 | 1.780 |

排序仍是 O(n log n)，昂贵的日期转换从按比较次数执行降为 O(n)。这组数据证明了可减少的 CPU 工作，不是正式首页提速 171 倍，也不是当前真实内容量或 p95；同步任务并行运行时的主机负载也不受本实验控制。实施还应覆盖 DST 边界、异常日期处理与既有时间线测试，不能借机改变排序语义。

## 3. 让社交封面查询跟随实际输出页

位置：`src/server/social/runtime.ts` 的 `socialTimelineSnapshot()` 在分页前调用 `covers()`；`src/server/social/covers.ts` 的 `withSocialCovers()` 按全部 snapshot.items 构造 wanted。作品页在 `works-repository.ts` 之后才筛选、排序和切页，首页在 `home-feed-v2-core.ts` 之后才与内容混排。封面装饰保留原 snapshot.version，本身不参与当前游标身份。

原型让现有作品分页器先选页，再调用同一个 `withSocialCovers()`。243 条虚构作品、每页 16 条，分别比较默认、B 站按播放、小红书按点赞各两页；提供非空且通过既有格式校验的虚构封面映射。六页的完整 DTO、总数和下一页游标均与当前实现相同。每页 wanted 从 243 降到 16，查询本身仍为一次批量查询，没有改为逐卡片查询。

这不是查询耗时测量：SQL 中仍有带资格的 publications／collections 投影，不能把 wanted 的缩小倍数当作 SQL 提速倍数。实施需覆盖合集优先封面、无图／待登记为 null、显式撤回、来源改变、两页之间变化以及首页混排；结束版本检查、RLS 和资格不得因为“只查一页”而削弱。封面映射查询与 F28 对象字节读取是两个边界，后者已有独立任务。

## 4. 搜索下一阶段先减少反复抽取，再选择索引

位置：`20261017131837_scoped_search_parts.sql` 的 `read_search_parts()` 逐条读取合格正文并调用 `search_parts()`；`website-repository.ts` 再把片段组成一个临时 paragraph，交给 `searchContentSnapshot()` 重建纯文本、NFKC 归一化和扫描。因此，即使只返回五条结果，工作仍与全部选定正文规模有关。

可比较三个方案：

- 保持现状，作为结果与性能基线，继续保留即时资格及引用判断。
- 在内容批次生成／变更时准备不可变的文字片段，保留 `[text, internalHref, mediaId]` 依赖标记；读取时仍检查当前条目、祖先、引用目标、媒体和政策版本，再做原匹配。这样把重复 AST 遍历移出访客请求，但需要新生成协议、旧批次兼容及存储大小验证。
- 对预生成文字做候选索引，再以当前完整脱敏逻辑精确复核匹配、总数、排序与分页。GIN／pg_trgm 可以作为候选，但没有可提取三元组的 LIKE 模式会退化；一两个中文字符、NFKC、多段文字拼接及资格撤回必须单独验收，不能把英文长词的实验套到中文搜索。[PostgreSQL pg_trgm 官方说明](https://www.postgresql.org/docs/current/pgtrgm.html#PGTRGM-INDEX)。

本轮没有预设索引一定胜出，也没有生成索引、运行新的数据库基准或安装迁移。还可让搜索匹配核心直接接收已过滤文本，去掉“文字 → 临时 AST → 文字”的中间对象；这是 CPU／分配优化，不能替代前面的 SQL 侧工作减少。

## 5. 结构与观测服务于减少重复工作

- 用有类型的读取方法区分 metadata、selected body、version、search parts，逐渐替代 `scopedReader()` 按 SQL 字符串正则改写函数名和参数的接线；保持旧协议摘要与能力握手，不把已安装迁移改字节。
- 将资格投影与脱敏、查询选择与游标身份、事件排序、纯文本匹配拆成可独立对比的函数；`ContentRepository` 公开契约和 provider 失败行为保持。近期 F27 的作品排序已抽出 helpers，沿用这条方向，不重建整套服务。
- 当前 `traceContentRead()` 主要包 detail／metadata。扩展搜索／列表／树／首页的阶段耗时、SQL 次数、池等待和返回字节，日志只保留固定操作、类别和计数。先区分 SQL、网络、池等待与 CPU，才能决定下一轮是索引、批量还是纯函数优化。
- 社交路径能看到角色检查、合集版本、快照、封面版本及封面查询多段串行往返。可评估合并读取协议；角色／资格检查不应为了少一次往返直接永久缓存。没有测得连接池排队前，也不直接增大 pool.max。

## 已合理的部分与验收边界

课程目录已按最多 5,000 条批量读笔记，`studyTree()` 用父 ID 分组 Map，不是每个节点扫描全数组；24 层界限让每条路径的复制有界。这里暂不为算法名义重写成另一棵树。当前首页两类来源已并发读取、内容正文已只为选中项批量装载、页面的 React.cache 已限定单次渲染，也不重复实施这些优化。[React cache 的请求范围](https://react.dev/reference/react/cache#caveats)、[Supabase 批量查询指导](https://supabase.com/docs/guides/database/query-optimization)。

本轮三项原型均只在本机执行，未进入应用；原始结果与脚本保存在忽略目录。第一轮原型源码替换匹配不完整导致工具编译错误，修正替换后完整对比通过；不是仓库代码失败。后续应用实现仍应分别走受影响回归、一次规定的完整 check／build、最终集成与上线检查；不能用本报告的微基准放行正式部署。
