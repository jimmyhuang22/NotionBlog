# 内容存储与 Notion 同步候选方案

记录日期：2026-10-11。状态：架构讨论，待选择。

补充：用户已确认网站同时供中国内地和海外访问者使用，并倾向第一阶段先跑通 Vercel + Supabase，以后按需求迁移。具体准备见 [首阶段联调](VERCEL_SUPABASE_TRIAL.md)；免费组合与本地同步尚未验证内地网络，长期区域和同步执行位置结合 [部署候选比较](DEPLOYMENT_OPTIONS.md) 评估。

用户正在考虑保留 Notion 编辑内容，同时把数据同步到自有数据库，由网站后端读取数据库。本文件比较候选方向；现有 provider、公开规则和部署选择继续按已确认配置运行。后续内容整理与前端编辑登记仍有效。

## 当前工程已经具备的后端

当前 Next.js 工程同时包含前端与服务端。服务端通过 Notion SDK 读取来源，检查公开资格、课程父链和媒体归属，转换正文 AST，再由统一内容入口及 HTTP API 供页面使用。因此当前选择的差别是是否增加持久存储，以及网站请求是否实时依赖 Notion。

```text
当前：访问者 → Next.js 服务端 → Notion API → 统一内容 DTO → 页面
候选：Notion → 后台同步任务 → 自有数据库／媒体存储
                            → Next.js 服务端 → 页面
```

页面布局与组件在当前架构下已经可以定制。独立数据库主要改善查询性能、搜索索引、多来源合并、发布版本与可用性；它不会自动补齐前端正文渲染，也不会解除外部平台的读取权限限制。

若只做低频更新的文章网站，也可以同步为静态内容或受控发布快照，不一定需要关系数据库。本项目还有学习层级、作品库和多来源时间线的需求，因此数据库是更值得试验的长期候选。

## 两种方案的取舍

| 方面 | 请求时读取 Notion | 同步到自有数据库 |
| --- | --- | --- |
| 编辑方式 | 继续在 Notion 编辑 | 仍可在 Notion 编辑 |
| 访问时的依赖 | 依赖 Notion 的响应、限流及父链读取 | 主要依赖网站服务、数据库及媒体存储 |
| 最新内容与撤回 | 当前实现每次重查来源资格 | Notion 中的变更需同步后反映；需确定可接受延迟 |
| 搜索、聚合与多来源 | 通过服务端适配实现，需考虑上游读取成本 | 可以用索引、关系与独立事件记录支持 |
| 工程与运行成本 | 组件少，但实时读取耗时 | 增加数据库、存储、任务、备份与同步维护 |

现有完整课程目录的单次优化后测量约 28.7 秒，仍受网络、限流和逐节点校验影响；它不是延迟保证。自有数据库可把这些读取放到同步阶段，再从数据库读取已经处理的目录；具体速度仍需实际部署测量。

Notion 官方提供 Webhooks，可通知实体变化；事件包含标识及变更元数据，接收后仍需通过 API 读取最新内容。同步应校验事件、去重、重试，并定期核对数据以补齐变化，不能把通知当作完整数据库镜像。[Webhooks 文档](https://developers.notion.com/reference/webhooks)、[API 限制](https://developers.notion.com/reference/request-limits)。

## 推荐讨论方向

长期倾向保留 Notion 为人工内容的编辑来源，增加网站自己的数据库与发布存储，复用现有 TypeScript 后端。首阶段以单向同步为主，明确每个字段的维护来源：标题、正文和个人评分由人工维护，外部平台的自动数据由对应导入任务维护，网站公开规则由既定发布配置控制。

课程、周次、活动和知识子页应保存真实父子关系，不能扁平化。同步只处理已经批准的内容与所需最小元数据，保留当前动态整来源和学习允许列表规则；私人源标识与原始信息只在服务端使用。正文继续转为现有 AST，图片若要摆脱 Notion 临时地址，需另外同步实际文件到对象存储。

未来外部平台活动可以直接写入自有事件表。是否再写回 Notion 属于另一个选择；已有时间线方案中的 Notion 写入路径仍是候选。避免起步时把所有字段设计成双向编辑，以免标题、评分或公开状态互相覆盖。外部接口准入与实际数据能力仍须分别联调。

增加数据库不要求重建独立后端项目。现有 contracts/ 和 src/lib/content/ 可继续作为前端边界，增加数据库 provider，把 Notion 适配器作为同步任务的读取与转换模块复用。

## 部署候选及下一步

一种托管组合是 Vercel 运行现有 Next.js 网站与服务端，Supabase 提供 PostgreSQL 和文件存储；同步任务先手动触发小批量试验，再评估分批后台任务及 Webhooks。持续或较长的同步工作需独立评估任务运行时间、重试和调度能力，不能在页面访问中执行完整导入。[Next.js on Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs)、[Supabase Database](https://supabase.com/docs/guides/database/overview)、[Supabase Storage](https://supabase.com/docs/guides/storage)。

托管位置、套餐与费用尚未选择；选择时需结合预算、区域、文件量、流量及备份需求。数据库备份和对象文件备份应分别核对。

在实施前，先明确更新延迟与撤回语义。Notion 删除、归档或授权变化需在通知或核对成功后更新网站状态；自己后端的立即下架入口可以更快阻止后续访问。同步失败应记录并展示管理状态，一次上游读取错误不能直接视为所有内容被删除。若要求每次访问实时向 Notion 重验，则仍会保留当前上游依赖；新方案不能未经确认改变现有撤回承诺。

可用一类动态和一棵课程树做数据库试验，验证同步重跑、更新、删除、父链、公开规则与媒体，再切换统一 provider。这个阶段复用已有工程，不需要同时开发完整内容编辑器或多租户平台。

## 免费套餐与同步任务位置补充

2026-10-11 核对官方文档。以下为试用建议，尚未创建托管项目、购买套餐、迁移数据或启用定时任务。

| 服务 | 起步套餐 | 主要额度及限制 |
| --- | --- | --- |
| Vercel | Hobby，0 美元／月 | 个人非商业用途；包含 100 GB Fast Data Transfer、100 万 CDN 请求及函数调用等额度，仍有 CPU、图片转换及其他资源限制 |
| Supabase | Free，0 美元／月 | 每项目数据库 500 MB、文件存储 1 GB；普通出站流量 5 GB 与缓存出站流量 5 GB 分别计量；最多 2 个活跃项目 |
| 同步执行端 | 已有本地常开设备 | 不增加云服务器租金，仍有设备电费、网络、任务维护和备份成本 |

来源：[Vercel Hobby](https://vercel.com/docs/plans/hobby)、[Supabase Pricing](https://supabase.com/pricing)。Supabase 免费项目在一周不活跃后可能暂停，且不包含自动备份；免费额度不等于可用性承诺。数据库与媒体应安排独立备份并验证恢复。

首批文字动态、课程层级和少量压缩图片适合先验证免费套餐是否足够；目前没有导入后的数据库大小、图片体积及真实访问流量数据，不能保证所有栏目长期免费。图片原件、视频和重复快照可能比文字先耗尽存储或流量。超过额度或需要更稳定运行时再评估升级，当前 Vercel Pro 标价 20 美元／月，Supabase Pro 基础标价 25 美元／月；用量、额外项目与税费另行核对。[Vercel Pricing](https://vercel.com/pricing)、[Supabase Pricing](https://supabase.com/pricing)。

候选运行路径为外部来源 → 本地同步进程 → Supabase 数据库／媒体 → Vercel 现有网站与服务端。同步进程可复用 TypeScript 读取与转换代码，由操作系统定时调度；macOS 可使用 launchd。[Apple 定时任务说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)。轮询方式只需向外发起 HTTPS 请求，不要求公网 IP、入站端口映射或把本地设备暴露给访客。

Vercel Hobby 的 Cron 每个任务最多每日执行一次，无法直接配置分钟级周期；本地执行端可以承担较频繁或较长的同步工作。[Vercel Cron 额度](https://vercel.com/docs/cron-jobs/usage-and-pricing)。后续若采用 Notion Webhooks，可由公开云端入口验签及入队，本地执行端主动取任务；这不是起步时必须实现的组件。

试验阶段可考虑约 15 分钟的增量任务，辅以较低频的完整核对；实际频率应按来源能力、限流、数据量和期望时效测量后确定。更新、删除、归档、授权变化与祖先公开资格不一定由同一种增量信号覆盖，不能把任务周期直接承诺为撤回延迟上限。

执行端睡眠、断网或停机时，任务需停止更新并在恢复后重试；云端网站可继续读取最后一次成功发布的数据，前提是托管服务及数据库仍正常可用。需要防止任务重叠、重复写入和半批数据发布，保存最近成功时间及失败状态；一次读取失败不能把已有公开内容当作全部删除。需要即时下架时，另实现网站自己的发布控制入口。

Notion 和外部平台读取凭据只给同步执行端，数据库写入权限只给可信服务端并尽量缩小范围；浏览器仅获取现有公开 DTO。后续切换数据库 provider 时，网站请求是否仍需 Notion 重验应作为明确决策，不能自动扩大公开范围或改变当前资格检查语义。
