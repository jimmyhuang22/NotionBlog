# 历史同步与快照清理实现审阅

2026-10-22。本文记录五个旧私人仓库实现请求在干净仓库迁移后的收编条件。旧请求编号不属于本仓库；原源码、运行回执、目录和精确版本映射继续保留私人。

本轮审阅基于新 `develop` 的实际源码、旧请求的实际远端头、逐文件三方对照和离线实验。结论是**五项均继续保留，分成同步与清理两组准备新的实现请求**。本轮没有完成实现收编，也不批准直接合并旧分支、安装运行包、恢复任务或部署。

## 同步组的整合门槛

1. 在新 develop 上移植必要差异，保留后续发布前来源复核和失败处理。三方文本可自动合并不等于行为兼容；不得用旧整文件覆盖新逻辑。
2. 先保留既有冻结兼容表及当前校验器。旧请求修改多份历史摘要表，且 `capture-release-compatibility.ts` 与其测试存在实际冲突。新的兼容能力、固定生产者、允许差异及测试资料要单独审阅，不能放宽摘要检查或引入旧 Git 父链。
3. 离线临时副本中，映射移除、原批次保持、逐页重验证和课程重投影行为能够运行；当前校验器仍对旧课程转换返回 `RELEASE_INVALID`。这证明参考实现可用于收编，也证明临时副本不是可安装版本。
4. 新库历史协议测试已经使用固定公开源码资料。旧测试／主机打包方式不能重新依赖新库中不存在的旧 Git 对象；新运行包必须独立绑定实际源码、转换器、配置、预算和回退输入。
5. 真实生产继续使用原 owner 的固定输入及外层程序。源码收编不替换这些路径，不消费旧运行窗口，不恢复来源，也不改变发布资格。

## 清理组的整合门槛

保留规划、归档和执行三层边界。旧 #439 的 `deleteChunkSQL` 是要求调用方持锁、校验归档与保护集的底层工具；不能脱离这些条件直接当作自动清理入口。旧 #464 在服务端重验保护集和目录摘要，并通过独立角色限制调用，是后续自动入口的参考。

当前搜索派生表存在指向原记录的 `ON DELETE CASCADE`。本轮在离线数据库中用当前迁移的实际建表语句复现：新增外键先使旧目录摘要检查拒绝操作；仅在临时数据库明确登记这项变化后，原归档／恢复流程通过，六行原负载删除另触发两行派生删除，三个受保护的派生行保留。级联语义见 [PostgreSQL 外键说明](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK)。

旧 `deletedRows` 只统计五张原负载表的直接删除，不包含派生级联，不能解释成全部物理删除、WAL 或耗时。已有私人安装记录包含针对搜索外键的独立审阅；不能把本轮离线实验说成新云端安装或重新批准启用。后续针对实际环境分别核对：

- 当前目录、外键、触发器、派生数据能否重建，以及原归档恢复范围；保持目录变化即停止，不能盲改预期摘要。
- 级联工作量、响应／时长预算及原有锁竞争；原六表恢复证明不能扩大解释为完整数据库备份。
- 当前公开缓存的触发器、事件消费者及外层绑定；不得把旧无缓存环境的成功回执当成当前组合验收。
- 原停止记录、未知写入与恢复程序。即使源码收编完成，也保持停止，直至另有具体运行授权。

## 工作树审阅

本轮重新盘点旧 Git 登记的 172 个工作树：7 个存在跟踪或未跟踪修改，161 个含忽略内容，4 个满足“detached、无修改／忽略内容、已进入旧 main 与 develop”的 Git 条件；这些计数有重叠。

同时只读核对了进程命令及打开目录、实际 Dagu 服务与定义路径、同步／清理／缓存运行输入、固定程序摘要和选定运维元数据引用。原维护运行包的 13 个配置摘要全部匹配，其中八个维护文件与本次受审 #464 相同。进程信息只保留相关路径与 PID，不保存环境或完整命令。

四个 Git 候选仍在迁移保留清单中；选定范围的无进程引用不证明没有所有者或其他外部引用。原根又包含新检出、备份和既有运行入口，因此本轮保留全部目录，不执行 detach、prune、删除分支或清空忽略文件。候选路径和逐项目录归属仅放私人报告。
