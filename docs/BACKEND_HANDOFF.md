## 前端怎样调用后端

所有页面都是 `force-dynamic`；同一请求内的重复读取用 React `cache` 去重，不跨请求保存。

| 页面 | 服务端调用 | 浏览器调用 |
| --- | --- | --- |
| 首页 | `getTimeline({ limit: 16 })` | `GET /api/timeline?limit=16&cursor=…`；展开动态时 `GET /api/content/status/[slug]` |
| 动态页 | `list("status", { limit: 12, year? })`、`getStatusYears()` | `GET /api/content/status?limit=12&year=…&cursor=…`；展开同上 |
| 学习首页 | `list("course", { limit: 50 })`，有下一页时继续，最多 4 轮 | 无 |
| 课程布局（课程页与其下所有笔记共用） | `getCourseMetadata(course)`、`getCourseTree(course)` | 无；同一门课内切换笔记不会重新读目录 |
| 课程页 | `get("course", course)` | 无 |
| 笔记页 | `getCourseMetadata(course)`、`get("study-note", slug)` | 无 |
| 作品库列表 | `list(kind, { limit: 24, status?, order? })` | `GET /api/content/[kind]?limit=24&status=…&order=…&cursor=…` |
| 作品详情、相册页 | `get(kind, slug)` | 无 |
| 相册列表 | `list("album", { limit: 50 })`，目前只取一页 | 无 |
| 博客列表 | `list("post", { limit: 12, tag? })` | `GET /api/content/post?limit=12&tag=…&cursor=…` |
| 文章页 | `get("post", slug)`，直接使用详情的 `adjacent` | 无 |
| 关于页 | `getPage("about")` | 无 |
| 搜索页／弹出式搜索 | 搜索页 `search({q, limit:12, kinds?})` | `GET /api/search`；弹出式搜索每次取 6 条，完整页每次 12 条 |

前端已处理的行为，后端可以依赖：

- 分页只用 `hasMore` 与 `nextCursor`；带游标请求返回 `INVALID_QUERY` 时自动不带游标重取第一页并提示，不会循环重试旧游标。
- `RATE_LIMITED` 显示繁忙，其余失败显示可重试；都由读者点击触发，没有轮询。
- 目录、笔记与相邻文章链接全部 `prefetch={false}`；首页时间线与课程目录各自独立加载，失败只影响本区。文章相邻项由详情提供，不再另扫文章列表。
- 图片一律用普通 `<img>` 指向 `ImageAsset.src`，没有经过图片优化；看大图与放大用的是同一个 `src`，不会另取更大的版本。
- `null` 的日期、评分、张数、学期都显示为“未记录”一类文字，不补值。
- 作品库的排序用列表已有的 `order`：`date-asc`、`title-asc`，默认不传。筛选或排序变化时前端会清空游标。

新增的一个服务端函数，部署时请知悉：`src/lib/render/actions.ts` 的 `renderSnippets`。展开的动态在浏览器端渲染，它把正文里的代码与公式片段发给这个函数，换回高亮与排版后的标记。它只转换传入的片段，不读取任何内容，不涉及公开资格；每次最多 24 个片段、合计 6 万字符，不合格的输入返回空结果。它以 POST 发到当前页面地址，任何人都可以直接调用，目前没有限流。

### 二、“关于”页

用户已确认：增加“关于”页，内容来自 Notion 里由用户维护的一个普通页面（不是数据库记录），和笔记一样在 Notion 里修改后自动更新。版式用户已选定单栏：和首页一样居中的头像、标题、简介与社交图标，下面一张卡片放全文并注明更新时间。

需要，形状可调整：

- 一个按固定标识读取单页的入口，例如 `contentRepository.getPage("about")`；没有配置、未公开或已归档时返回 null。建议形状：

```ts
interface SitePage {
  /** 固定标识，首批只有 "about"。 */
  slug: string;
  title: string;
  updatedAt: string | null;
  document: ContentDocument | null;
}
```

- 来源是私有配置里指定的一个页面，单独授权、单独公开；它的子页面不自动公开，正文里指向未公开页面的链接照常显示为不可点击。需要用户在 Notion 里新建这一页并告知位置。
- 正文沿用现有的 `ContentDocument` 与站内媒体路径，三个 provider 行为一致，同步任务把这一页纳入发布批次。
- 一个单独的开关，或者“未配置即关闭”：没有这一页时前端不显示导航入口，`/about` 显示找不到。
- 演示数据里补一页虚构的关于页，标明演示。
- 头像、名字、简介与社交链接仍来自私有站点配置，不需要放进这一页。

前端只在服务端读取，不需要浏览器接口。地址用 `/about`。

### 三、首页时间线合并接口

> 复验记录（2026-10-12，前端）：直接读内容源的只读预览里，全部栏目打开时首页时间线 90 秒没有返回，页面一直是占位骨架，没有报错。切到数据库读取后请一起复验首页的首屏时间。

用户认可的首页设计：一条按时间倒序的时间线，文字动态为主，其他栏目的更新作为小卡片穿插其中（看过某部电影、在读某本书、通关某个游戏、新相册、新文章、新项目）。[时间线同步方案](TIMELINE_SYNC_PROPOSAL.md) 中的外部来源（视频、笔记、游玩活动）以后也进入同一条线。

现状：前端用现有的 `list()` 在服务端合并出“最近”一屏（动态 12 条加每个已启用栏目各 6 条，最多显示 16 条）。它不能跨栏目翻页，栏目多时读取次数也会增加，同一作品同一天的多次更新没有合并。

建议新增一个按时间合并的入口，例如 `getTimeline(query)` 与 `GET /api/timeline`，返回 `Page<TimelineEvent>`：

```ts
type TimelineEvent =
  | { id: string; type: "status"; occurredAt: DateRange | null; entry: StatusEntry }
  | {
      id: string;
      /** 决定卡片上的动词与配色，例如 movie-watched、book-reading、game-cleared、album-new、post-new、project-new。 */
      type: string;
      occurredAt: DateRange | null;
      title: string;
      summary: string | null;
      cover: ImageAsset | null;
      /** 站内详情地址；没有站内页面时为 null。 */
      href: string | null;
      /** 外部来源的原文地址；站内内容为 null。 */
      externalUrl: string | null;
      /** 一行补充信息的原始数据，例如评分、进度、平台、张数；缺失为 null。 */
      rating: Rating | null;
      progressPercent: number | null;
      detail: string | null;
    };
```

前端需要的保证：

- 只包含已启用栏目且通过各自公开规则的内容；栏目关闭时该类事件不出现，首页自然退化为只有动态。
- 全局按 `occurredAt` 倒序，未知时间在最后；游标分页，跨页不重复。
- 事件时间用真实发生时间（观看、阅读、游玩、发布），不能用采集时间冒充。想看、想读、想玩与状态未知的记录不算活动，不进入时间线。
- F44（2026-10-21）：`book-read`／`book-given-up` 取 `readingDate.end`，单日记录取 `start`；`book-reading` 取 `start`。`game-cleared`／`game-platinumed` 只取手填 `playedDate.end`，单日记录取 `start`；`playedDate` 为空不生成完成事件，不能用平台最近游玩、采集或编辑日期补位。`occurredAt` 为 `{ start: 选中端点, end: null, precision: 原精度 }`。
- 影视观看与游戏在玩的时间保持现状；只改时间线投影，不改栏目列表、年份分组、游戏 `archiveDate` 或 Notion 来源。当前已发布批次读取时重算，不需重采；新投影版本使旧时间线与首页混排游标失效。代码集成及线上生效分别以进度回执为准，见[完成日期决策](decisions/2026-10-21-timeline-completion-dates.md)。
- 同一作品同一天的多次更新合并为一条。

接口就绪后，前端把数据来源换成这个入口并加上“加载更早”，卡片与样式不变。

### 四、为已完成页面接入真实数据

这些页面已经做完，等真实适配与栏目开关。用户已确认的顺序：游戏优先，其次影视、书籍，相册与博客在后。打开栏目需要用户另行确认公开范围。

前端依赖的约定：

- `href` 必须是 `/library/movies|books|games/[slug]`、`/photos/[slug]`、`/blog/[slug]`，页面按这个结构取 slug。
- 状态筛选值前端在用：影视 `watched`、`wishlist`；书籍 `reading`、`read`、`wishlist`、`given-up`；游戏 `playing`、`completed`、`wishlist`。`completed` 继续表示通关与白金。
- 排序值前端在用：`date-asc`、`title-asc`，以及默认的日期倒序。未知日期在两种日期排序里都排在后面。真实适配请一并支持，或说明不支持哪一个，前端去掉对应选项。
- 游戏的 `playedTime` 请给有效时长：有平台统计时用平台时长（真实的零也算），没有时用历史手填值，都没有为 null。前端显示为“N 小时”或“N 分钟”，不换算。多个平台的记录目前只显示 `platforms` 列表与一个总时长；如果要按平台分别显示时长或奖杯，需要新增字段，请先和前端对一下形状。
- 作品封面按 2:3 裁切显示，相册封面按 4:3；游戏有不少横图，会被裁切，有 `width`、`height` 更好。
- 相册正文里的图片请作为顶层 `image` 块或放在 `columns` 中，前端会把连续图片排成网格；`photoCount` 未计算时保持 `null`。
- 博客需要先确定文章来源；`summary`、`tags`、`publishedAt` 都会显示，按 `tag` 筛选已在用。

接入后前端会按真实封面比例和数量再调一次网格，并在真实数据下复验排序与翻页。

### 五、列表与详情的几项小补充

互相独立，可以分开做，也可以随别的项目顺带完成。

- **总数**。`Page<T>` 没有总数，除动态外前端只能显示“已显示 N 条”。如果能低成本提供可选的 `total`，前端显示“N / 总数”。
- **相邻文章**。文章页现在靠读文章列表找相邻两篇，超过 200 篇后就找不到了。建议在详情里直接给出，例如 `ContentDetail` 上可选的 `adjacent?: { newer: ContentLink | null; older: ContentLink | null }`，按列表的默认顺序。有了它前端就不再读列表。
- **站内搜索**。列表接口没有关键词参数，前端没有做搜索。数据库方案下如果方便，请提供一个按标题与正文文字检索的入口，范围限于已公开内容，说明支持哪些栏目和返回形状，前端再设计界面。
- **行内公式**。块级公式已支持，行内公式没有对应的内容类型，现在只能显示为普通文字。如果来源里有行内公式，建议在 `TextRun` 上加一个可选标记，例如 `equation?: true`，`text` 放表达式，前端负责排版。

## S12：作品与首页读取期限

作品 v1／v2 API，以及首页混排 API 和 v2 服务端首屏，使用同一次 **7,000 ms 服务端读取期限**。API 调用 repository 不重置期限；社交身份、能力、快照及当前页封面 SQL 的排队与执行共享剩余时间。这个值给响应序列化留出余量，不是承诺平台调度、事件循环阻塞及访客网络合计必定小于 8 秒。

超时或取消时，正在使用的本请求数据库客户端销毁，其他请求的客户端不受影响；晚取得的连接直接归还，不执行 SQL。pg-pool 的待取回调仍由原连接超时清理，不能把 API 已经失败表述成数据库服务端已取消所有工作。不改变池容量、角色权限、TLS、资格或撤回检查。没有请求预算的冻结采集／维护调用保留原路径。

失败保持 `503`／`CONTENT_UNAVAILABLE`、`private, no-store` 和 `noindex`，新增 `Retry-After: 1`；不自动重试或回退演示、原图、部分首页。非法筛选／旧游标仍为 400，关闭来源仍为 404，成功 DTO 保持。前端现有“重试加载”可以继续使用；慢提示与取消旧请求的交互由前端处理。

每次服务读取输出 `CONTENT_LIST_READ`：固定 operation、outcome、durationMs、limitMs；失败 SQL 输出 `CONTENT_SQL_FAILURE`：acquire/query 阶段、deadline/aborted/driver 等原因、允许的 SQLSTATE 和池计数。不输出 SQL、游标、参数、正文、凭据或原始异常；平台请求关联由托管日志提供。上线后复用自然请求日志核对整日及实际 HTTP 总耗时，不以服务计时替代完整网络时间。

原 19 秒故障的精确关联仍未证明。七秒边界已发布，后续请求日志已能通过同范围 CLI 读取，并再次观察到作品请求等待连接和查询超时；不能据已部署关闭故障。

作品 v2 的 database 路径按现有模块连接池容量准入完整读取：一次准入覆盖角色／能力、快照、分页和当前页封面，避免并发请求每执行一段 SQL 就排到其他请求后方、一起耗尽期限。等待准入仍消耗原七秒预算；取消或过期的等待立即移除，获准后继续检查当前资格，不复用其他请求的快照、封面或权限结果。活动请求排空清理后才释放名额；不增加数据库连接数。非法筛选在排队前校验；无预算的冻结调用保留原路径。首页和媒体读取不进入此作品准入队列。

准入失败记录 `SOCIAL_READ_QUEUE_FAILURE` 的固定原因、容量、活动和等待数；没有 SQL、参数、游标或原始异常。详见[排队修复记录](progress/2026-10-20-social-read-queue.md)。该后续候选的正式发布、24 小时完整请求观察及反馈方翻页复验仍需接续；不重新采集内容或图片。
