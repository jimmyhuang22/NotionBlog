# 内容读取计时

需要排查详情HTML与数据API差异时，可在受限reader的本机生产进程显式设置`CONTENT_READ_TIMING=enabled`。默认关闭；不为日常验证修改云端配置或创建部署。`dev:real`有自己的变量白名单，不应通过给它migration／writer环境取得计时。

`CONTENT_READ_TIMING`日志只记录operation、公开内容类型、成功／错误、总耗时和固定阶段调用数；不含路由slug、请求编号、来源、SQL、参数、DTO、连接目标或原始错误。可在受控HTTP追踪中关联请求，避免将并发不同页面的日志混在一起。service/runtime阶段有嵌套，不能直接加总所有阶段；database-acquire包括池等待与新建连接，database-roundtrip包括网络和数据库内部资格／查询，均不等于数据库纯执行时间。

作品库页面已有Claude提供的`read(type, slug)`，供metadata与正文共用。使用原始type和slug字符串，不能用各次新建params对象作为cache键；仅一次Server Component渲染内去重，不是跨请求缓存。普通API继续通过统一repository做各自当前读取。错误／null结果在同一渲染内共享，后续HTTP请求重新取值与资格。无需再叠加一个后端cache入口。

排查次序：核对部署与provider→分别记录首次／暖态HTML、JSON、RSC及SQL调用数→检查Proxy、布局与重复详情读取→必要时对受限只读SQL另测计划执行时间。没有数据时保留初始化／渲染等剩余部分为未知，不把客户端可见三秒直接写成SQL三秒。前端预取与回访缓存需要另测真实浏览器导航，服务端curl不能证明浏览器五分钟命中。

本机对照要保持生产构建、同一受限reader、相同页面与顺序，并把首次进程和已建立连接分开。一次实际对照中，共享入口使metadata／正文的详情读取从两次变一次，暖态RSC完整响应约1.30秒降到0.91秒，但首次HTML标题数据仍约3.36秒；不能据此把首次等待记为已解决。Proxy与页面运行环境分别建立连接，资格预检之后才进入页面；单次渲染去重不会消除这些连接和检查。DTO投影不足1毫秒，也没有证据把主要等待归于正文渲染。优化应接续有界预取和真实导航复验，而不是跳过资格或增加无失效策略的跨请求内容缓存。
