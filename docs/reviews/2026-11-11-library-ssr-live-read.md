# 2026-11-11：作品 SSR 共同读取接入与成本复验

本报告记录 SSR 接入阶段的离线验证；后续集成状态见[默认关闭集成记录](../progress/2026-11-11-library-compact-merge.md)。默认配置仍为 legacy。精简读取的优势是减少大列表传输；本轮没有证明它在直连或热缓存场景更快，不建议默认开启。

## 接入与权限边界

- `readLibraryFirstPage` 从 SSR 页面调用，使用经栏目权限包装的 service。具备 `readLibraryPage` 能力时走独立实时路径，完成态 DTO 不进入 `publicRepository` 缓存；关闭栏目零读取。没有能力的 provider、显式 legacy 配置保留原编排和缓存；新路径失败不会自动切回旧实现。
- 先取精简选择器，在 JS 中沿用既有年份、过滤、排序和 w1 游标。以当前 run/revision、配置/策略、物理身份和完整候选集合指纹，重新检查全部资格并读取所选完整元数据。
- 本地或云端封面准备完成后，再执行一次同样的完整最终检查。之后只有同步 DTO 投影和受限投递尺寸附加，没有异步 I/O。准备阶段不能替换正文、标题、链接或媒体身份；移除的媒体被清除，新出现且尚未准备的媒体拒绝返回。
- 只有可选的本地年份计算/结构校验可以降级。失败时保留请求年份，隐藏年份切换；成功但年份不存在时去掉年份并重新分页。空页也做最终检查。SQL、资格、游标、取消和封面失败均不能被降级吞掉。
- 新 SQL 为独立可选协议，摘要必须由安装所有者显式登记。私有 schema/state 不开放给网站，状态表启用 RLS；只有 nb_reader 获得两个读取 API 的执行权限。固定 search_path，沿用既有 qualified/published 资格函数。做法参考 [Supabase 函数权限说明](https://supabase.com/docs/guides/database/functions)。

最终保证的边界是**最终 SQL 的语句开始快照**。在该语句开始后才提交的撤回，正在执行的请求仍可能返回旧快照；下一次请求排除撤回内容，旧游标失效。原实现多次分页读取可能在后续 pin 检查中报错，因此不能宣称竞态报错时点完全一致。媒体 HTTP 入口继续做自身的实时权限检查。

## 测量范围

3,000 条合成作品，每条 2,400 字节摘要，24 个封面描述符，首屏 24 项。保留冻结原实现（后端基线 `0b0c862`）和既有 4 MiB 实验；当前工作区基线为 `41a02cf`，其新增 develop 变更是阅读视觉调整。三个方案共用请求内读取预算，对每种情况交错执行三轮，取中位数；每样本独立 Node 进程/reader。内存另测单样本。

计时覆盖页面的数据准备：列表、年份、回退、封面映射和最终检查；不含 React/HTML 生成、浏览器图片下载、TLS/连接握手、CDN、Notion 或真实 Storage 流量。协议字节使用 PostgreSQL TCP 接收计数，排除启动和 SET ROLE，包含 SQL 返回协议。受限网络是本机 20 MiB/s 代理与每次执行器调用 40 ms 附加延迟。容器限制 2 CPU、2 GiB，work_mem 4 MiB。

**云端映射限制**：运行正式 `databaseDisplayProjectionSql` / `readDisplayAssets`，通过本地合成 SQL 函数返回批量合规描述符。没有本机私有生产映射迁移，未测其实际计划，也没有连接项目云端。这可测接口、批量载荷和往返成本，不能等同线上映射 SQL 的成本。

**缓存限制**：运行正式 `readPublicProjection` 和真实本地 `nb_cache_api.read_stamp`；缓存存储端口是内存 Map，热样本先预热，预热不计时。未测托管 Next 缓存服务时延。年份失败不会存成成功的年份缓存，因此“已预热”的年份失败场景仍需要重新读取。角色隔离首次检查另列，常规表按已有 runtime 已通过检查计。

正常首屏相对未缓存原实现，精简读取减少约 **88.5%** 协议接收量、**27.6%** 耗时；相对冷缓存原路径，耗时减少约 **35.7%**。无效年份回退相对未缓存原路径，耗时减少约 **63.7%**。4 MiB 减少往返但仍传输整集合；精简在这组受限网络里更快。

热命中则有明确退步：原路径正常页只查两个 stamp、返回 428 B，约 48 ms；新路径仍需四次 SQL、约 608 ms。这里比较的是不同的重新检查强度，不能删除最终检查来追平缓存数字，也不能用冷缓存收益掩盖此代价。

## 直连、封面与隔离检查成本

| 准备模式 | 原实现 SQL / ms | 精简 SQL / ms | 4 MiB SQL / ms | 精简接收量 |
|---|---:|---:|---:|---:|
| 无投递准备 | 2 / 220.5 | 2 / 312.7 | 1 / 193.2 | 0.899 MiB |
| 本地 manifest（合成 2 ms） | 2 / 309.7 | 3 / 413.4 | 1 / 253.5 | 0.975 MiB |
| 云端批量描述符夹具 | 3 / 278.0 | 4 / 547.5 | 2 / 221.0 | 0.989 MiB |

直连结果没有显示精简方案提速，且三轮波动明显，例如云端夹具精简为 353–685 ms，原实现 231–334 ms。不把这些小样本作为稳定百分比承诺；数据库重复指纹扫描和最终重查会消耗 CPU。新方案依旧是 O(N) 选择器读取与 O(N log N) JS 排序。

同样 24 个描述符，云端适配器只做 **1 次批量映射 SQL**，未产生逐图 N+1；比本地准备增加 **14,671 B（约 14.3 KiB）** 的协议接收。受限网络单独补测本地准备精简为 574.8 ms，云端为 608.4 ms；批次波动下，这个差值只作参考，不是生产映射的稳定耗时估计。准备后最终检查额外返回当前页完整元数据，本轮约 77.5 KiB，这是权限保证的实测成本。

角色隔离设为 enforce 且 runtime 尚未检查时，每个冷路径增加 1 次 SQL、66 B；云端精简首屏为 5 次 SQL。热缓存预热已完成该检查，不会每页重复。这里不涉及 Supabase 客户端实例复用。

另测单样本 Node 进程峰值 RSS：原实现 235.6 MiB、精简 129.7 MiB、4 MiB 188.4 MiB。它包含进程基线，不是私有堆用量或数据库内存；本轮没有重复宣称此前的数据库内存结果。

## 建议与后续条件

1. 保持本轮实现默认 legacy、留在工作区审核。精简路径适合大集合、较高网络时延或经常触发年份回退的场景；热缓存占主导时当前成本不占优。
2. 在决定启用前，补实际私有云端映射函数计划/载荷与托管 Next 缓存命中率、时延数据。任何云端安装、配置变更和上线仍需后续明确授权，本次未执行。
3. 若后续批准集成，再审核新协议摘要与 reader 权限，按 v2/scoped 条件安装并登记独立迁移，最后单独启用 `DATABASE_LIBRARY_PAGE=compact`。读失败不自动切回 legacy；回退应是明确的配置决定。

20,000 条 / 16 MiB 选择器和 16 MiB 当前页元数据上限仍保留，超限失败；封面投影沿用既有遍历上限。内容或选择器在读取阶段频繁变化时可能导致更多 INVALID_QUERY；默认不重试。媒体映射若在准备后同 ID 改变尺寸，本次只保留已经准备的尺寸提示，实际媒体 HTTP 读取仍使用其当前权限/映射检查，不能把尺寸提示视为媒体访问授权。
