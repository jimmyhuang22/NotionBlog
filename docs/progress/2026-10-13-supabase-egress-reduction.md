# 2026-10-13：减少数据库全栏目回读（Codex）

编辑登记：独立 `codex/supabase-egress-reduction` 分支，范围为 v2 database reader 的查询投影、同步结束的 reader 回执检查与针对性测试。前端、公共 DTO、冻结 SQL、权限、来源、图片生成和同步排程不在本项范围。

- 官方用量分项及数据库调用统计指向连接池响应，不能把上游图片下载字节或本机原件缓存读取字节算成 Supabase 出站流量。实际项目、时间窗口、调用数和诊断证据仅保存在私有目录；统计累计值不冒称单日计量，也不把查询次数直接等同网络字节。
- 旧 reader 在读取单篇详情、单页元数据和年份统计时仍取回整个栏目；动态的 `read_snapshot(false)` 也包含全部正文。详情与元数据改用既有 `read_content` 精确选择，课程元数据不再读取课程正文。
- 列表和年份统计不传全栏目正文。动态使用内部的字段索引排序、筛选和计数，只传当前页完整正文生成预览；跨两次读取检查同一 run／revision，变化时拒绝结果并要求重启分页。超过一批的元数据读取固定原 run／revision，保留二万条上限。
- 既有函数先验证最新发布资格，再由固定 SQL 将允许链接与媒体列表裁到返回记录中出现的引用。JavaScript 继续执行原来的引用清洗；未知或撤回引用仍不可用，不增加持久缓存或放宽到期检查。
- 完整快照接口仍可用于必要的搜索、时间线和一次性导出。空快照与同步后的回执核对只返回所需版本／摘要，避免附带全站链接和媒体 ID。
- 真实验证使用现有受限 reader、严格 TLS、只读可重复读事务。首次组合读取设置 1 MiB 响应预算；后续仅对修改后的动态索引与单页列表追加约 194 KB 的验证。没有图片下载、云端写入、全站逐篇验收或发布。
- 样本比较：单篇动态响应从全栏目约 1.27 MB 降至约 2.6 KB；年份索引约 90 KB；十二条列表两次读取合计约 104 KB。单篇测量采用解析后的 JSON 大小，后两项采用 PostgreSQL 实际 JSONB 文本字节；均是样本响应体积，不冒称平台整月账单或全站流量已经同比下降。

接口／provider：公共 DTO、游标格式和版本标识保持；仅 database v2 的返回投影收窄。v1、mock、Notion provider、Storage 与缩略图交付规则保持。

验证：15 项针对性数据库／流量测试验证体积、完整 DTO 和预览一致、嵌套引用、撤回、分页中途变更及空版本检查；Node 24 的 `npm run check` 通过 1,232 项测试、类型／三项协议，最终 487 文件隐私扫描与两项记录格式检查通过。`npm run build` 与 40 份服务端追踪隐私检查通过。新检出的依赖最初借用同锁文件目录的符号链接，Turbopack 拒绝越过工作区解析；改为本检出的实际依赖目录后构建成功，没有因此改动应用或构建配置。平台检查结果在合并请求上核对。

限制与下一项：本项未合并或部署网站，也未替换固定同步 release；旧部署和已有冻结 release 不会自动取得修复。全栏目元数据及必要的完整快照仍有读取成本，未来可另做数据库分页／搜索索引；已消耗的额度不能通过优化追回。按用户分支／发布约定完成审阅后，将同一修复接入实际网站版本与固定运行版本，再观察后续小时用量；不通过反复全量验收制造额外流量。
