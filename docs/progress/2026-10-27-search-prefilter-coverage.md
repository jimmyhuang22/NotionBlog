# 2026-10-27：搜索必要片段预筛与数据库往返排查（Codex）

编辑登记：用户要求继续排查正式搜索的 2–6 秒延迟并优化。从最新 develop `45429a3` 创建独立分支，只修改搜索预筛 helper、相关测试与本项说明；不改共享 DTO、Unicode 数据表、迁移、权限、栏目或生产设置。上一轮[正式发布](2026-10-27-search-production-release.md)保持其实际结果。

已定位一个保守回退：`python` 因末尾可能与生成占位文字的开头相接而完全停用预筛；含标点、长词或完整正则过大也有相同行为。空 probe 的版本五函数会调用原完整搜索投影，不能因为设置了 filtered-scope 就假设每个词都走小投影。

现有严格 TLS 受限 reader 做只读核查，只返回数量、尺寸、服务端计时和一个 EXPLAIN，没有下载正文：当前 `python` 路径生成 2248 条候选、7,642,787 字节结果文本，服务端约 3774 ms、客户端往返约 3971 ms；以可证明必要的 `pytho` 预筛后为 74 条、1,179,477 字节、约 964／1162 ms。相同安全片段的 EXPLAIN 执行约 877 ms，规划约 0.09 ms；这是小量单次诊断，非稳定分位数、纯 CPU 或生产整体收益。它支持优先减少数据库完整投影，不能把主要慢耗时归结为客户端网络；EXPLAIN 读法参见 [Supabase 官方说明](https://supabase.com/docs/guides/troubleshooting/understanding-postgresql-explain-output-Un9dqX)。

实现：完整查询不适合时，选择其最长可安全表示的必要片段，保留完整 Unicode 逆像和原 2 KiB 正则限制，并限制每次最多 128 次构造尝试。片段不能与任一生成占位文字相交；没有安全片段或运行时不兼容时仍读取原投影。既有结果保护、版本五能力、完整匹配／排序／分页与撤回复核保持。新 helper 为 `python` 生成的条件与本次实测 `pytho` 条件完全相同；不需重新安装数据库。

验证：针对 Unicode 展开、占位文字两侧合成匹配、完整分页、qualified／published 两模式、实际减少 SQL 候选与撤回的 16 项定向检查通过。首轮新测试夹具没有产生预期的一个真匹配，已补足该夹具并复测受影响文件；生产没有运行这些测试夹具。搜索修正单独版本集中运行一次完整 check，3054 项全部通过，零失败／取消／跳过；标准 build 与 49 条服务端构建隐私追踪通过。相关说明链接、记录格式及差异检查通过。

本轮真实数据库解密接收约 5 KB（含计数和 EXPLAIN），另读公开官方文档约 0.2 MB 及少量 GitHub 元数据。没有数据写入、数据库安装、生产配置或业务定时任务变更，没有扩大旧 S13 采样或重复旧发布。
