## 栏目加载框架的兜底

11-03 的渐进式栏目导航（#261）在点栏目链接后约 60 毫秒盖上一层栏目加载框架，同时把原页面和页脚设为不可操作，直到新地址落地才撤掉。详情页的变暗切换有 15 秒放弃时间，这层框架没有。如果导航一直没落到目标地址（请求卡住、被中止），页面就会一直被盖住、无法操作。

现在框架建立时同时启动 15 秒计时（与详情页的 `GIVE_UP_AFTER` 相同）。到时如果它仍是当前切换，就按原有的 `drop` 撤掉框架和进度条，恢复原页面的可操作状态和读屏属性。导航之后若仍然落地，照常显示新页面。被别的切换替换或正常落地时，`drop` 会清掉这个计时。

## 怎么验证的

- 本机演示数据开发服务器，无头 Chrome，1280 宽，从首页点导航里的"动态"：
  - 在浏览器里扣住 `/status` 的请求：0.5、3、14.5 秒时框架都在，原页面不可操作；15.6 秒时框架与进度条撤掉，原页面可操作、读屏隐藏已去掉，地址仍是 `/`；放行请求 3 秒后，地址变为 `/status`，没有残留框架；
  - 不扣请求的正常切换：0.5 秒内到达 `/status`，框架已撤掉。
- 本机 Node 26.11.1，以低优先级运行：`npm run build` 通过，49 份服务端追踪隐私检查通过。`npm run check` 共 3304 项，3271 项通过，33 项失败，都在 5 个后端测试文件里（website-v2-runtime 17、qualified-shared-budget 9、capture-recovery-host 4、full-collection-host 2、capture-recovery-admission 1），原因是这台机器的 Node 26 加载不到 `libnode.147.dylib`，或发布校验要求 Node 24（`RELEASE_INVALID`），与本改动无关。类型、协议与 lint 通过，另补跑 `npm run privacy:check` 与记录格式测试。
- 只用演示数据和 Chrome 验证过，没有测 Safari 和真机。

## 作品页偶尔慢一次：诊断（未改代码）

线上实测（11-07）：

- 默认作品页无论空闲 0～30 秒，整页约 0.3 秒，说明缓存命中时不受空闲回收影响；
- 没人访问过的筛选组合第一次 1.9～2.7 秒，立即重复约 0.3 秒；
- 11-03 实测过一次作品"加载更多"冷请求 4.8 秒，之后同一请求 0.53 秒。

原因：`socialTimelineRepository` 经 `publicRepository` 按调用参数缓存，平台、排序、翻页位置的每个组合各占一份缓存。缓存未命中时，`createSocialWorksRepository` 先通过 `socialTimelineSnapshot` 读出全部作品，再在内存里筛选、排序、分页，最后核验选中作品的封面。因此：

- 默认页刚读过全部作品，换一个筛选或往下翻一页，又要从数据库重读一遍；
- 每次发布清空缓存后，第一个访客要付这笔开销；
- 社交只读连接池在 transaction 模式下最多 1 条连接、空闲 5 秒回收，冷读时往往还要先重新建连（Codex 11-04 测得内容池重新建连约 0.43 秒；内容池已延长到 60 秒，社交池仍是 5 秒）。

可选修法，属于 Codex 的范围，需他或用户确认：

1. 把全部作品这份数据（不含实时核验封面的函数）在同一版本戳和标签下单独缓存一次，各筛选、翻页都从它里面筛，封面核验仍在选出作品后实时进行。要确认这符合 `works-repository.ts`"不保存资格"的约束：现有按参数缓存的结果已经包含核验后的封面，单独缓存作品数据并不会比它更旧。
2. 每次发布清缓存后，由消费端顺手请求一次首页和默认作品页预热，避免第一个访客撞上冷读。
3. 社交只读连接池的空闲回收和内容池一样延长到 60 秒，能省掉冷读里的重新建连。

动态、相册页首字节约 0.45 秒，大部分是一次约 150 毫秒的版本戳查询加上访客到源站的往返。再降要缩短服务器到数据库的距离，或减少每次请求都要做的版本戳查询，同样属于 Codex 的范围。
