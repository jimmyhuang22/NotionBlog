# 2026-10-13：平台检查不重复已有答案的内容（Claude）

编辑登记：Claude“分支合并检查”对话，按用户在选项里的决定落实，并在后端的 [集中 CI 改动](2026-10-13-ci-batched-development.md) 先合入 develop 之后，改到它的工作流之上。范围：`.github/workflows/check.yml`（共享的检查配置，用户指定由本对话修改；触发方式、运行器标签、权限、并发与超时都保持后端那一版）、新增 `scripts/ci/check-plan.ts` 与 `tests/check-plan.test.ts`、[运行说明](../GITHUB_ACTIONS_RUNNER.md) 一节、`AGENTS.md` 检查说明里的一句、需求文档与开发接手说明各一句、一条[决策记录](../decisions/2026-10-13-do-not-repeat-verified-checks.md)；另外把 `CLAUDE.md` 和前端接手说明里“平台检查通过后合并”的旧说法改成与现行规则一致。没有改依赖、契约、fixtures、栏目开关、应用代码、SQL 和运行器本身的安装。

## 起因

检查在当天改到 Mac mini 的自托管运行器，同时只接一个任务，一次约 12 到 13 分钟，09:35 UTC 队列里排着 8 个请求。另一个前端对话数过检查记录：托管主机停摆之前真正跑起来的 473 次、约 2075 分钟里，166 次、约 683 分钟是请求合并之后在目标分支上整套再跑的那一遍。

## 中途的变化

我开这个请求时（09:46 UTC），工作流还是每个请求、每次 push 都跑；用户在同一轮选项里还选了“运行器用本机期间，合并只要求平台检查”，我也写进了规则。10:05 UTC 后端按用户在它那边说的“不过 CI，直接合并，然后继续开发”合入了集中 CI：日常进 develop 不再逐个触发平台检查，以按影响的本机验证为准，develop 约每两小时集中检查一次，main 的合并请求与 push 保留自动检查。两个决定在“日常合并以什么为准”上相反，以后一个为准。所以这个请求撤掉了“只要平台检查”的全部规则文字，只保留不重复检查这一项，并把它接到新的触发方式上。

## 改了什么

- **工作流多了一步计划**（`Plan the checks`，在安装依赖之前）：运行 `node scripts/ci/check-plan.ts plan`，输出三种之一，后面的步骤按它执行。
  - 整套：与原来完全一样，也是判断不了时的结果。
  - 已验证：检出内容的树编号两周内通过过整套，后面的步骤全部跳过。集中检查之后它管的是：develop 没变时的下一个两小时批次、内容与刚检查过的 develop 相同的发布请求、发布合并后 main 上的那次 push。
  - 只改文档：相对它所接续的提交，只有 `docs/` 下的文件和根目录 `.md` 变了，只跑 `node --test tests/record-entries.test.ts` 与 `npm run privacy:check`，不安装依赖。现在只可能出现在 main 的合并请求与 push 上。
- **通过后记一笔**（`Remember this content as passed`）：把树编号记到运行器工具目录下的 `notionblog-check-passes/`。只改文档的通过只记“文档”范围，除非它所接续的内容通过过整套；“文档”范围不会让之后改了代码的检查被跳过。
- **保守的地方**：比较对象只认 GitHub 给出的关系（合并请求的合并提交的第一父提交、push 之前的分支顶端）；一次推上来多个提交、历史不完整、计划这一步自己出错，都跑整套并且不记录。检出改为取两层历史，仅用于这次比较。
- **文字**：`AGENTS.md` 写明“树相同才算同一个版本”，以及很快变绿时先读任务摘要；`CLAUDE.md` 与前端接手说明改成“按影响范围完成本机验证后自行合并，不等平台检查”，与 `AGENTS.md` 现行规则一致。

检查的内容没有减少：类型、三项协议、测试、隐私、构建与服务端追踪一项不少，只是不对同样的内容重复执行。

## 怎么验证的

- `tests/check-plan.test.ts` 8 项通过：哪些路径算文档；已通过整套的内容不再检查；改了代码或无法比较时跑整套；只改文档跑轻量检查且只跑一次；文档叠在已通过整套的内容上算整套；Node 主版本不同或超过两周的记录不采信；记录的读写、校验、不被窄范围覆盖与只保留 400 条；用临时 git 仓库验证合并请求与 push 两种比较关系，以及多提交推送、首个提交时不比较。
- 按工作流的调用方式在本机跑过一遍：没有记录时输出整套；记为通过后再计划输出已验证；参数不对时非零退出；没有持久目录时记录步骤什么也不做。
- 工作流文件能被 YAML 解析，触发方式与后端那一版相同。
- 合入最新 develop 之后，在工作分支上按现行规则集中跑了一次 `npm run check` 与 `npm run build`，结果写在合并请求里；改动过的文档里的本地链接都能解析。

## 限制

- 这套逻辑还没有在运行器上真正执行过。日常进 develop 的请求不再触发平台检查，所以它第一次执行要等下一次集中检查（手动或定时）：第一次应当是整套并留下记录；develop 不变时再跑一次应当显示已验证。合并后我会触发一次手动的 develop 集中检查来看前一半，并把结果补在合并请求里。
- “同样的内容两周内通过过就不再跑”假定检查是确定的、运行器环境在两周内没有实质变化。偶发失败的测试不会因此被再次暴露；Node 主版本变化会自动重跑。
- 运行器的工具目录是否在每次任务之间保留，是按运行说明里“依赖与工具缓存均可重建、暂不自动清缓存”理解的，没有登录那台账户核对；目录不保留时不影响正确性，只是每次都跑整套。
- 只改文档的判断按路径：`docs/` 下任何文件和根目录的 `.md`。放在别处的说明文件（例如 `scripts/` 下的 README）按代码处理，会跑整套。
- 定时批次要等新工作流随发布进入 main 才会自动运行，这是集中 CI 那项改动的既有限制，这里没有改变。
