# 2026-11-04：AWS 空闲后首页正文与数据库重连（Codex）

## 编辑登记与范围

- 从 develop `f3e778c` 建立 `codex/aws-home-idle-latency`。用户要求分离数据库重连与首页查询耗时，准备修复，正式发布前确认。AWS 线上测量使用 PR277 的应用版本和已启用回源 HTTP/2 的入口。本轮首页请求走 Node 回环，单独测应用和数据库。

## 测量

- 先跑八组首页回环对照，每组空闲后请求一次再立即重复。空闲 2／7 秒的四次完整响应中位数 166 毫秒。空闲 12／25 秒的四次为 587–600 毫秒，中位数 594 毫秒。八次立即重复中位数 163 毫秒。空闲组首字节中位数 15 毫秒，首页正文的延迟发生在流式首字节之后。对应时间窗的服务端日志也显示首页数据约 0.14 秒和 0.59 秒两个区间。
- 缓存命中时，首页仍要通过内容只读连接池执行版本戳查询，以确认缓存仍可用。在 AWS 的独立短进程中，沿用线上 Node、驱动、TLS 校验、实际 transaction pooler、只读账号、隔离校验和应用的 SQL 执行器。每轮预热后测 12／25／45／12 秒空闲与立即重复，各池单独计数。10 秒连接池四次空闲后都为空且重新建连，获取连接中位数 428 毫秒、事务往返 141 毫秒，整次读取 572 毫秒。立即重复获取连接约 0.1 毫秒，整次读取 141 毫秒。对同一 SQL 做六次只读 `EXPLAIN ANALYZE`，Postgres 执行为 0.24–0.31 毫秒。实际首页回环的额外耗时与重新建连吻合。
- 再配对记录 11 次首页请求与数据库 transaction pooler 端口的 TCP SYN 时间。空闲 12 秒的三次为 585–634 毫秒，与初始慢请求一样在等待期间都新建连接。两次空闲 7 秒和五次立即重复均为 156–187 毫秒，各自窗口内无新连接。只保留时间，无地址或流量内容。
- 额外测试空闲后先请求版本接口，接口自身花 0.57–0.66 秒。随后三次首页仅一次回到 0.16 秒，其余仍约 0.59 秒。这组交叉路由测试未稳定预热首页，不能用它来推断两个路由必然共享一次已建立的连接。

## 修改与验证

- 只给公开自托管运行时的共享内容只读连接池将空闲回收从 10 秒延长至 60 秒。保留最多两条连接、按需连接、空闲后回收、退出时关闭；社交池、其他执行环境、SQL、接口、provider、发布资格和版本戳读取保持原策略。依据 [node-postgres 连接池空闲回收定义](https://node-postgres.com/apis/pool)。
- 60 秒配置在相同四轮空闲下都复用了连接，整次读取中位数 140 毫秒。约 63 秒无访问后恢复正常回收并重连。此对照是 AWS 上的独立只读 SQL 探针，发布后仍须复测完整首页。
- 自托管真实启动配置的测试覆盖 60 秒、最多两条连接、零预建连接、退出关闭；普通环境仍由已有测试覆盖 10 秒。连接池、自托管生命周期及社交连接定向测试 12 项通过。
- AWS 回环 HTTP 响应合计约 0.91 MB，另有小量只读版本查询和日志。总云端用量估计数 MB，未单独计量。仅使用现有配置，测试结束后关闭临时数据库池和 SSH 会话。
- Node 24 完整 `npm run check` 通过 3304 项，无失败或跳过。普通 `npm run build`、本机公开自托管构建及断网 Linux AMD64 公开自托管构建均通过，各核查 49 个 server traces。Linux 复用匹配两份锁文件的已安装依赖，运行 Node 24.22.2，与 AWS 相同。
