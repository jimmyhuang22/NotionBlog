## 已确认与仍未知

对同一 11 秒日志窗口做一次聚合，唯一预计算取消事件明确匹配 **statement timeout**，不是该事件的用户请求取消或 lock timeout。原客户端设置为 5 秒服务端超时。日志未包含可用的内部函数阶段，不能据此认定排序、摘要、权限检查、锁或共享资源争用是根因。

两次 SQL 分别读取有限统计／配置元数据，以及对原游标执行不带 ANALYZE 的 EXPLAIN。派生表在填充接近结束时已有自动统计，估算 2,000 行、另有 245 行修改，不能以“新表完全没有统计”解释问题。当前计划通过既有索引读取再按 ID 排序；这是当下的规划结果，不是失败当时的执行轨迹。所有者会话的 JIT 关闭不代表已采样真实 reader 的会话设置，也不能当作排除所有计划问题的证明。

实际独立只读范围 27.8 秒内完成，返回约 5 KiB：1 次日志、2 次元数据 SQL、0 次托管完整搜索、0 次写入。生成入口仍关闭，原账本字节摘要保持一致。没有读取正文行至本机、重置统计、ANALYZE、修改配置、提权或开始持续观察。

## 本机横向对照

全部采用原迁移和 PGlite，数据为虚构动态，每条 48 个文本块；每个方案先准备一次，再三轮交替测量。每次返回规范化摘要，核对条数、投影字节和完整摘要一致；没有公开真实正文或身份。保留所有原校验、资格判断、顺序、数量／字节上限和缺项回原提取。

| 数据组与方案 | 暖 SQL 中位 | 决定 |
| --- | --- | --- |
| A：2,245 当前记录、40,410 条空正文历史记录，原提取 | 951ms | 对照 |
| A：现有预计算逐篇查表 | 471ms | 对照 |
| A：一次关联派生表 | 463ms | 相对现有预计算约 1.7%，不采用 |
| B：2,245 当前记录、无历史，现有预计算 | 466ms | 独立对照 |
| B：先排序 ID，再逐条取正文 | 465ms | 同组约 0.2%，不采用 |

以上计时包含 SQL 投影、规范化和摘要，排除驱动及 HTML；两个数据组不能混算，A 的历史正文为空，也不能模拟真实托管物理 I/O。A 的本机计划曾出现约 2.7 MiB 的磁盘排序；B 窄 ID 方案自身排序约 65 KiB、无临时块，但不跨组宣称消除了线上磁盘瓶颈。第二种改写增加逐条主键回读，整体收益不足。

独立组件聚合测得，读取已存摘要约 1ms，重算全部正文摘要约 109ms、片段摘要约 67ms。这些是本机组件下界，不是完整搜索耗时，不能与不同查询直接相加解释线上 5 秒。原逐篇路径的另一次带计时剖面也显示查表及完整性校验有实际成本；两份摘要仍必须保留，不能为提速信任陈旧或损坏片段。
