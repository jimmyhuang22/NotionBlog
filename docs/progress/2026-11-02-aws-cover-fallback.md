# 2026-11-02：定位作品小图回退原图的触发原因（Codex）

编辑登记：只新增本记录。接续[图片缓存核查](2026-11-02-aws-image-cache-audit.md)中未确认的回退原因，使用既有浏览器记录与服务器日志定位；未修改应用、前端、SQL、连接池配置、缓存策略或部署。

## 已确认的链路

1. 此前两轮打开／刷新作品页，浏览器分别出现18张、12张原图回退。相同时段、相同40个资产的服务器访问日志分别有18个、12个资产返回503；两轮失败资产集合与浏览器原图回退集合逐项完全一致，不只是数量相同。
2. 同时段有30条安全分类 SQL 失败记录：26条发生在等待连接阶段、4条在查询阶段。原因分别为27条deadline、1条query-timeout、1条aborted和1条未细分driver；故不能把每条都单独说成等待连接超时，但主要失败明确集中在连接排队与期限耗尽。
3. 该部署的社交 reader 使用 transaction 模式，代码将连接池上限设为1。失败现场连接数最多1、空闲0、排队最多24；图片整体期限为8秒，排队、身份／协议检查、资格读取、对象读取及读后复查都计入其中。
4. 已发布 main 的图片路径每次先查 reader 身份及协议，再查合集协议，然后读取封面绑定并在响应前复查；正常条件304路径也有这4次SQL往返。并发封面集中到该池时，浏览器即使已有图片，仍可能因这条校验路径排队超时而收到503。
5. `CoverImage` 的既有错误处理会在小图失败后将 `src` 切到原图；这发起另一个请求，且原图与小图不是同一个浏览器缓存条目。上一轮抽查的一组原图为896,083字节、小图84,374字节，说明回退还可能显著增加传输和等待。

因此，这两轮的直接触发原因是服务器图片请求失败，主要瓶颈为单连接下的数据库读取排队耗尽图片期限；可以解释已观察到的回退，无须假设缓存未开启、图片缺失或浏览器无故更换资产版本。两次现场均有成功304，正常缓存复用与部分请求失败同时存在。

## 验证边界与后续

按线上 `b9f39fb` 的实现核对路径，而非把 develop 尚未发布的读取事务改动当成线上实现。服务器访问日志不记录查询参数，单条记录不能独立区分小图与原图；本结论结合了两轮浏览器地址、精确资产集合、时间及SQL分类日志。未重新整页下载、压测、直连数据库或遍历媒体；本轮只读服务器日志，回传量为数十KB以内。

修复应优先减少保留完整资格检查前提下的数据库往返、为图片并发提供合理的排队与连接容量，并避免小图临时失败后再叠加昂贵的原图请求。具体查询、并发容量与回退行为需作为后续实现验证；不能仅放大期限或取消资格检查后宣称解决。本轮没有实施这些变更，也未声称全部性能问题已经解决。
