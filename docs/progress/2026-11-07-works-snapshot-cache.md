# 2026-11-07：作品页冷读——共享行数据、社交连接复用与清缓存后预热（Claude）

编辑登记：用户把作品页冷读的修复交给 Claude（"You do it"）。Claude 修改 `src/server/social/runtime.ts`、`src/server/social/reader.ts`、`src/server/social/works-repository.ts`（只改注释）、`src/lib/content/social-timeline.ts`、`src/app/api/internal/cache/purge/route.ts`，新增 `src/server/public-cache/warm.ts`、`tests/shared-social-rows.test.ts`、决定 [2026-11-07-shared-social-rows](../decisions/2026-11-07-shared-social-rows.md)，并在 `docs/PUBLIC_CONTENT_CACHE.md` 补一句。契约、SQL、迁移、DTO、发布资格、撤回流程、依赖、栏目开关与前端组件未改。

## 来由

诊断见 [栏目加载框架兜底的记录](2026-11-07-section-switch-giveup.md)。线上作品页没人访问过的筛选组合第一次要 1.9～2.7 秒，立即重复约 0.3 秒；11-03 测到一次"加载更多"冷请求 4.8 秒。原因是每个平台、排序、翻页组合各占一份缓存，未命中时都要从数据库重读全部作品；社交只读连接池空闲 5 秒就回收，冷读还常常要先重新建连。

## 改了什么

1. **共享行数据。** `socialTimelineSnapshot` 拆出 `socialTimelineRows`（只读行数据，每条 `cover: null`，不带请求内能力）和 `withLiveSocialCovers`（给行数据接上实时封面核验：每次核验都重新取一个已验证的只读连接，只核验选中的作品）。开启 tagged-v1 时，`social-timeline.ts` 用 `publicProjection("social", "socialTimelineRows", [])` 缓存行数据。作品页各组合、作品"加载更多"接口和首页混合时间线都从这份行数据里筛选。缓存关闭时走原路径，不多一次核验。
2. **社交连接复用。** 新增 `socialReaderRuntimePoolConfig`：只在自托管公开网站把社交只读连接池的空闲回收从 5 秒延长到 60 秒，和 11-04 的内容池一致。连接上限（transaction 模式 1 条）、按需建连与随进程关闭不变。
3. **清缓存后预热。** 清缓存接口在完成清除、返回响应之后，通过 `after()` 调用 `warmPublicPages()`：只在自托管公开网站、`PUBLIC_CACHE_ORIGIN` 是 http 回环地址、`SITE_URL` 是 https 时，顺序请求 `/` 与 `/works`，Host 取自 `SITE_URL`，与启动预热一致。同一时间只跑一轮，期间再清缓存只补跑一轮；每页最多 15 秒、2 MiB，读完正文，失败不记录、不重试。其他部署不预热。

撤回与版本边界：行数据和页面结果用同一个版本戳和日窗口，都挂 `social` 标签，清除时一起失效；读取过程中版本戳变化仍按原逻辑重试。清缓存事件只接受已提交的发布事件，所以预热时版本戳已经更新，撤回后的预热只会生成不含撤回内容的新页面。

## 预期效果（未在线上验证）

- 换筛选或往下翻页：从重读全部作品，变成读两次版本戳、两次身份核验和一次封面核验，预计从约 2 秒降到 1 秒以内。
- 内容发布清缓存后的第一位访客：首页与默认作品页已经预热过。
- 空闲 5～60 秒后的社交冷读省去约 0.4 秒的重新建连。
- 代价：缓存未命中时，行数据要多读一次版本戳和一次核验，约 0.3～0.45 秒。这只发生在每次清缓存后的第一次，而且通常被预热吸收。行数据超过约 2 MB 时不存储，退回逐次读取（最多 500 条作品，预计远低于此）。

## 怎么验证的

- 新增 `tests/shared-social-rows.test.ts`（4 项）：
  - 三组筛选的全部翻页只读一次行数据，每次列表都单独核验选中作品的封面，结果与直接读取一致；缓存里只有 `cover: null` 的行数据，不含核验函数；版本戳变化后重新读取；
  - 社交连接池只在自托管公开网站为 60 秒，其他情况保持 5 秒、其余参数不变；
  - 预热目标只在自托管公开、回环 http Origin、https 站点时成立；
  - 预热按顺序请求两个页面、带配置的 Host，并发清缓存合并为补跑一轮，请求失败不抛异常。
- 本机 Node 26.11.1，以低优先级运行：`npm run build` 通过，49 份服务端追踪隐私检查通过。`npm run check` 共 3315 项，3282 项通过，33 项失败，都是已知的 5 个后端测试文件，原因是这台机器的 Node 26 加载不到 `libnode.147.dylib`，或发布校验要求 Node 24（`RELEASE_INVALID`），与本改动无关。首次完整检查发现清缓存路由的 `next/server` 在纯 Node 下要写成 `next/server.js`，改正后相关的 7 个测试文件（46 项）通过。
- 没有在本机连真实数据库验证。实际耗时要等发布并安装到 AWS 后，在线上复测：冷筛选组合、"加载更多"、清缓存后的首页与作品页、空闲 10～60 秒后的作品页。
