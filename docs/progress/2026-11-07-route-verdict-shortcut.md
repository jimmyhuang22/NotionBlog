# 2026-11-07：栏目首页不再在首字节前查数据库（Claude）

编辑登记：用户让 Claude 继续处理"动态、相册页首字节约 0.45 秒"。Claude 修改 `src/lib/route-verdict.ts`、`src/middleware.ts`，在 `tests/route-qualification.test.ts` 补一项测试。路由规则（`qualify-route.ts`）、内部路由查询接口、缓存、SQL、契约与页面组件未改。

## 来由

线上首字节（11-07，各测 3 次）：首页、作品页约 0.16～0.18 秒；动态、相册、影视、学习约 0.31～0.46 秒，多出约 150 毫秒，正好是一次数据库查询。作品页的页面同样要等数据，首字节却快，说明多出的这段在页面渲染之前。

原因在中间件：它对 `/about`、`/blog`、`/photos`、`/projects`、`/library`、`/study`、`/status` 下的地址，先判断地址存不存在、有没有被撤回，以便不存在的页面直接返回 404。公共缓存开启后，所有这些地址一律走内部的缓存路由查询，要读一次版本戳。可是按 `qualifyRoute` 的规则，栏目首页（`/status` 不带 `focus`、`/photos`、`/blog`、`/projects`、`/study`、`/library/movies|books|games`）只看栏目开关就能判断，本来不需要读数据。公共缓存之前的直接判断路径就是这样。

## 改了什么

- 新增 `routeVerdictFromConfig`：用同一套 `qualifyRoute` 规则，在一个"任何读取都报告需要查询"的替身上跑一遍。不读数据就能下结论的地址直接返回"存在"或"不存在"；一旦需要读数据（详情页、带 `focus` 的动态、课程、笔记、学习项目、关于页）就返回 null。规则只写在一处，不会出现两套判断。
- 中间件先调用它，只有得到 null 时才走缓存路由查询（或缓存关闭时的直接判断），其余逻辑不变。
- 行为差异只有一处：栏目首页不再因为这次查询失败返回 503 替身页；栏目页自己有读取失败的提示，和公共缓存之前一样。详情页、撤回的 404 与查询失败的 503 不变。

## 怎么验证的

- `tests/route-qualification.test.ts` 新增一项：栏目首页判定为存在、全程不读数据；关闭的栏目与各种格式错误的地址判定为不存在；详情页、带 `focus` 的动态、关于页、课程、笔记、学习项目都交给完整查询；凡是能直接判定的地址，与用模拟仓库的完整判断结果一致。连同公共缓存与路由缓存的相关测试共 30 项通过。
- 本机演示数据开发服务器：`/status`、`/study` 返回 200；`/photos`、`/library/movies`（演示环境栏目关闭）、`/library/unknown`、`/status/extra`、`/about` 返回 404；`/status?focus=不存在` 仍走完整查询，返回 404。
- 本机 Node 26.11.1，以低优先级运行：`npm run build` 通过，49 份服务端追踪隐私检查通过。`npm run check` 共 3316 项，3283 项通过，33 项失败，都是已知的 5 个后端测试文件，原因是这台机器的 Node 26 加载不到 `libnode.147.dylib`，或发布校验要求 Node 24（`RELEASE_INVALID`），与本改动无关。

## 限制与下一项

- 需要发布并安装到 AWS 才生效。预期动态、相册、影视、学习的首字节从约 0.31～0.46 秒降到与首页相近（约 0.17 秒），要在线上复测。
- 详情页（单个相册、影视条目、课程、笔记）仍要在首字节前查一次数据库，以便不存在的页面返回 404。这是有意的，本次未改。
