# 2026-11-07：代码与公式渲染请求合并（Claude）

在浏览器里展开的正文和带公式的列表文字，原来每条各发一次渲染请求。动态页一屏有 20 条带公式或代码的卡片，就是约 20 次请求，滚动加载还会再来。这是[CSP 与渲染限流方案](../BACKEND_HANDOFF_PLAN.md)第 3 节的前置项：渲染入口改成同源路由、请求并行发出后，按访客突发 12 次、全站同时 2 个的初案，一次正常翻页就可能被拒。

## 改动

- 新增 `src/lib/render/batch.ts`：
  - 同一时刻（10 毫秒内）的渲染请求合成一次；
  - 两条请求里相同的代码或公式只发一次；
  - 仍遵守每次 24 项、合计 6 万字的上限，超出的分到下一次，一条正文不会被拆开；
  - 每次只有一个请求在途，在途期间新来的请求排进下一次；
  - 某一次失败时，只有这一次里的条目保留原文，下次需要时会重新请求。
- 新增 `src/lib/render/browser.ts`：浏览器端唯一的渲染入口。
- `browser-document.tsx`（展开的正文、关于、预览块）和 `typeset-inline.tsx`（列表文字里的公式）改走这个入口。
- 服务端 `renderSnippets` 的输入、输出与上限不变，后端接口和响应头没有改。服务端渲染页面里的代码和公式不经过这条路。

## 限制与下一项

- 只在演示数据下验证过：演示动态原本没有带公式的列表文字，浏览器计数用的是临时加了公式的本机演示数据，没有提交。真实动态页上一屏的请求数，要等上线后再数。
- 被限流的处理现在还用不上：旧入口拒绝时不会说明原因，只会出错，而出错已经按失败处理（保留原文，下次再请求）。Codex 新增限流路由后，由 Claude 把 `browser.ts` 里的发送函数换成该路由；`RATE_LIMITED` 必须当失败处理，不能当成空结果。
- 下一项：Codex 修 Nginx 的访客地址链，再加限流路由并删除旧 Server Action；限额等本项上线后，用真实动态页的请求数来定。
