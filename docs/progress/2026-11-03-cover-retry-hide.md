# 2026-11-03：封面重试期间不再露出破图标记（Claude）

编辑登记：Claude 修改 `src/components/cover-image.tsx`、`src/components/library-grid.tsx`、`src/components/use-image-failure.ts`。契约、接口与媒体路由、fixtures、依赖、栏目开关、全局入口、CSS 与后端代码未改。

## 来由

审查 Codex 的图片修复（#254、#258、#266）时发现：小图请求失败后，封面会等 600 毫秒再重试一次同一张小图。等待期间，`CoverImage` 仍然挂着失败的地址。Chrome 对有尺寸、有替代文字的失败图片会画破图图标和边框，所以这段时间露出了破图标记。这违背了组件"封面不露出浏览器破图标记"的约定。

正文图片和影视/书籍封面用的 `useImageFailure` 会在等待期间摘掉地址，但实测这样仍会露出破图标记：Chrome 遇到有尺寸、没有地址的图片也画同样的占位，即使替代文字为空。

## 改了什么

- `useImageFailure` 在等待重试期间改用内嵌的 1 像素透明图作地址，并把 `retrying` 交给调用方。透明图立刻加载完成，浏览器不画任何占位。站点的内容安全策略允许 `data:` 图片。
- `CoverImage` 改用同一个钩子，不再自己维护重试状态。等待期间同时去掉 `srcset`，否则浏览器会立刻按 `srcset` 再请求一次。透明图的加载事件不算封面已显示，等待期间仍保留柔和底色块。
- 影视/书籍封面（`library-grid.tsx`）同样忽略透明图的加载事件，等待期间书脊占位保留。
- 正文图片没有净改动，钩子已经替它处理。
- 重试规则不变：只有已登记的 v2 小图和社交 s3 小图重试一次，不回退去拉原图；两次都失败时显示原有的失败状态。

## 怎么验证的

- 本机 Node 26.11.1，以低优先级运行：`npm run build` 通过，49 份服务端追踪隐私检查通过。`npm run check` 共 3292 项，3259 项通过，33 项失败。失败集中在 5 个后端测试文件（website-v2-runtime 17、qualified-shared-budget 9、capture-recovery-host 4、full-collection-host 2、capture-recovery-admission 1），原因都是这台机器的 Node 26 加载不到 `libnode.147.dylib`，或发布校验要求 Node 24（`RELEASE_INVALID`），与本改动无关，留给平台检查。类型、协议和 lint 通过（改动文件无警告），另补跑 `npm run privacy:check`（2279 个文件）与记录格式测试，均通过。
- 本机演示数据开发服务器，无头 Chrome，1280 宽。演示图片的地址本来不会触发重试，为了验证，临时让 `/mock-media/*` 也生成小图地址并走重试分支，验证后已还原，没有提交。在浏览器里拦截小图请求，返回 503：
  - 作品页 20 张封面，只让第一次请求失败：重试期间 20 张都是透明图、保留底色块，截图里没有破图图标或边框，约 0.9 秒后全部显示；
  - 作品页全部失败：重试一次后落到作品卡片的空白封面；
  - 动态页正文图片，只让第一次失败：重试后显示；全部失败：显示"图片暂时无法显示"。
- 影视/书籍页在本机演示环境里栏目关闭，没有在浏览器里验证 `library-grid.tsx`。它用的是同一个钩子，改动只有忽略透明图的加载事件这一处。

## 限制与下一项

- 只用演示数据在本机验证过，只测了 Chrome，没有测 Safari 和真机。
- 同一次审查发现的后端问题不在本改动范围，属于 Codex：每条数据库查询有四次依次往返，一条约 290 毫秒；浏览器只缓存图片 5 分钟，之后每张图确认一次约 0.7～1 秒；首次打开时导航栏预取全部栏目。
- 栏目加载框架（`page-switch.tsx`）没有 15 秒兜底，风险低，本次未改。
