# 2026-10-21：搜索能力隔离与计时匹配修复

用户要求继续定位并修复受控候选问题。本次从最新主线整合搜索草稿，保留已有社交媒体修复；课程和前端接口不变。原监控已完成并归档，原候选及封闭窗口不重跑。

## 已确认的问题与处理

- 可选搜索能力原来属于所有首次读取的共享前置条件；扩展缺失、失败或等待时，也会阻止课程和目录读取。基础与可选搜索就绪状态现分开，搜索成功后可复用基础就绪结果，等待／失败则不传播给普通读取。冷首次搜索仍只有一次合并能力检查；普通读取先发生时，首次搜索另检查一次，双方同时冷启动最多各一次，后续能力检查复用。内容、资格、祖先、撤回、版本检查仍逐次读取。
- 原私有测量脚本直接用完整 `x-vercel-id` 匹配 CLI 日志请求 ID，又只读汇总消息。安装 CLI 的 `extractVercelId` 取最后一个 `::` 后的部分，且请求日志的全部消息在 `logs[]`，汇总只选其中一条。新增无网络离线解析器，按此格式匹配部署／采样请求并遍历消息，拒绝含糊、截断、异常或越界输入，只留下计时白名单和采样序号。

旧实现已用相同虚构回归条件复现两种可选模式下的普通读取失败。修复覆盖冷首次／并发、失败重试和缺失扩展数据库中的真实课程详情、目录、撤回；搜索一致性、权限、版本竞争和过期仍由原测试验证。日志解析器覆盖带路由前缀、嵌套多条计时、汇总重复、错误部署／请求、格式与大小限制和私有字段剔除。

另以同一门虚构课程和 64 个笔记做三个模式的横向对照：on-demand、filtered、precomputed 的课程详情＋目录均为冷首次 3 次 SQL（含能力检查）、后续 2 次；完整 SQL 和参数序列及 DTO 全部相同，普通读取均未检查可选搜索能力。这是确定的查询路径与往返对照，没有把并行运行时的本机耗时当成性能收益。

验证采用固定离线入口、清除云凭据并拦截外部 Node 连接：定向 34 项和日志／并发专项 12 项通过；完整检查的类型、协议通过，2,408 项测试中 2,407 项通过，唯一失败是本记录标题漏日期，修正后对应 3 项记录检查全部通过，没有因纯文档修正重跑全套。原失败日志保留。后续补完 1,500 文件源码隐私检查；webpack 构建及 45 项服务端追踪隐私检查通过。所有应用改动均经本次全量测试与构建，平台 CI 与线上复测另计。

## 证据边界与下一项

上述修复消除确定存在的依赖耦合与计时匹配缺陷。能力函数只是小表摘要检查，不能称其已解释上一轮课程完整 HTML 中位数增加 21.59%。旧窗口原始日志按隐私约束未保存，仍是零条已归属计时，不能补造旧 SQL／连接池归因；新增解析器的虚构测试也不是线上计时证据。
