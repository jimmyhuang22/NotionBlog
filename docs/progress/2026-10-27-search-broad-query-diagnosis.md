# 2026-10-27：宽泛搜索数据库耗时与单次序列化优化（Codex）

编辑登记：用户要求继续优化“学习”等宽泛查询的数据库耗时，避免与详情页首次加载重复。本项基于 develop `8177f62` 沿用已有只读诊断，改动仅限搜索结果体积保护的内部 SQL 包裹与解码、对应回归和说明；未实现新数据库扩展、同步接线、模式切换或发布。详情页入口、共享 DTO、既有迁移与公开裁决保持原有实现。

## 已定位的成本

既有六条生产搜索计时中，宽泛查询的应用耗时约 2.61–3.14 秒，数据库往返约 2.41–2.82 秒；取连接约 17–72 毫秒，池最大等待为零。正文整理约 107–139 毫秒，匹配约 70–82 毫秒。阶段可能嵌套，不能把这些值相加为总耗时。

本轮通过现行数据库连接，在 PostgreSQL 17.11 的只读事务中对实际搜索函数及其子步骤做计数和 EXPLAIN ANALYZE。只返回数量、尺寸、函数定义与计划，不下载正文，不创建临时函数，不安装扩展或修改角色／项目设置。函数内计划一般只显示 Function Scan／Result，需要拆出内部语句才能看清成本，参见 [Supabase 官方说明](https://supabase.com/docs/guides/troubleshooting/running-explain-analyze-on-functions)。本轮未开启全局嵌套日志。

| 测量步骤 | 本次服务端耗时 | 观察 |
| --- | ---: | --- |
| 现有资格检查、读取与排序 | 101 ms | 2,248 条；已有 Bitmap Index Scan，排序落盘约 2.4 MB |
| 加上原始 JSON 文本转换与正则预筛 | 452 ms（累计） | 保留 290 条候选 |
| 加上正文片段提取与聚合 | 1,416 ms（累计） | `search_parts` 调用 290 次，函数节点累计约 861 ms |
| 完整函数及包裹查询 | 1,450–1,533 ms | 分别执行的诊断查询，不能当作生产稳定延迟 |
| 单独统计原始 JSON 文本转换 | 364 ms（含资格与排序） | 全部记录共生成 24,406,137 字节文本；没有把这些文本传回客户端 |

290 条候选最终生成 68,074 个片段，片段 JSON 文本约 3.16 MB，完整搜索投影约 3.28 MB。即使页面只展示 12 项，当前仍须把所有候选的可搜索内容交给原匹配器计算完整数量、排序和分页。上述拆分查询有自己的 CTE 和汇总开销，差值是定位线索，不是严格可加的 CPU 分账；EXPLAIN 也不能代替客户端传输计时，见 [PostgreSQL 官方说明](https://www.postgresql.org/docs/17/using-explain.html)。

当前主要重复工作是：每次搜索重新序列化全部 JSON，再为命中的数百条候选重新遍历正文生成片段。资格与连接池不是本次的主要优化目标；排序落盘存在，但不支持先调大全局内存或连接池的结论。

## 已实现：搜索结果只序列化一次

原体积保护先物化 JSONB，再连同文本尺寸物化一次，最终把 JSONB 交给 PostgreSQL 的输出函数再次序列化。现在只物化 `result::text` 一次，尺寸判断与传输共用该文本；原搜索函数仍只执行一次。应用适配器核对返回文本的 UTF-8 字节数后，用 JSON.parse 恢复原值，再交给原有读取器与通用响应预算。超限不返回文本，SQL NULL 与 JSON null 分别保留零字节和四字节计量，损坏响应返回原有安全错误，不带入私有文本。

此改动只作用于搜索 HTTP 已启用的 `bounded-v1` 保护；不增加调用、不放宽 13 MiB／4 次限制，不修改数据库函数或安装对象，也不影响详情、时间线和未启用保护的路径。

另一次受限 reader 的严格 TLS 只读会话，对同一快照以 old/new/new/old/old/new 顺序执行六次 `EXPLAIN (ANALYZE, BUFFERS, SERIALIZE TEXT)`。此选项实际执行输出序列化，但不向客户端传正文，参见 [PostgreSQL 17 EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)。

| 包裹 | 服务端执行耗时（ms） | 输出序列化（ms） | 临时写块（8 KiB） |
| --- | --- | --- | --- |
| 原实现 | 2782、1481、1463 | 21、24、34 | 每次 1903 |
| 单次文本实现 | 1397、1388、1508 | 10、7、10 | 每次 1503 |

中位数约 1481→1397 ms（5.7%）；第一条原实现有明显冷启动／预热差异，两个序列的样本也有交叉，不能据此承诺稳定收益或现网秒数。每次少写 400 个临时块，约 3.2 MiB，输出体量相同（计划报告 3206 KiB）。这项改动减少了可避免的包裹成本，未解决每次重建正文片段和全部预筛文本的主要成本。EXPLAIN 不包括网络传输，尚未发布到线上。

## 后续建议：按内容版本准备搜索投影

新增可重建的私有派生表，按 `run_id + record_id + parser_version` 保存两项纯内容结果：与现行规则一致的原始预筛文本，以及保持顺序的搜索片段（包括链接与媒体守卫）。不保存查询命中、公开资格或撤回判断。旧快照内容不因中央 deny 改变而重新计算原始片段；公开与引用资格继续在每条查询中现算。

建议分三部分实施：

1. **内容更新时准备**：从数据库中已存记录生成派生行，不接收外部传入的派生文本，不重新采集 Notion、不下载图片。首次准备当前快照；后续复用现有同步／增量变更集，新增和变更记录重算，未变更内容可搬运派生行。同一 run 内的内容替换也必须同步失效或重算旧派生行，不能只检查主键存在。阶段与原有运行锁配合，不另开并行 writer。派生行缺失或解析版本过旧时，查询按该条记录回到现有计算，不能漏结果，也不把“准备未完成”变成发布失败。
2. **查询时减少计算**：先取得有界的合格记录身份，保留现行 20,000 条限制；以已准备文本做相同的安全预筛，再读取匹配记录的片段。排序优先携带小字段，避免把整份正文带入全部记录的排序。保留当前候选全集，不提前 LIMIT 到首屏。
3. **沿用现有裁决与保护**：链接、媒体 owner、中央 deny、祖先链及快照有效性仍实时核验；应用继续使用现有 Unicode 规范化、完整匹配、排序、游标、总数和末尾版本复核。13 MiB／4 次结果读取保护及期限／取消不放宽。保留原函数与模式，新能力先默认关闭，以便回退。

新增私有表启用 RLS，不给 anon、authenticated 或 reader 直接读表权限；准备操作只通过受限入口绑定实际记录和运行范围。派生表随内容清理，不改来源公开语义。增量发布会生成新 run，必须明确复制或重算该 run 的派生行，不能只凭记录 ID 跨版本复用。

准备文本的逻辑体量本次约 24.4 MB／快照，另加全量片段；实际 TOAST 压缩、索引和多版本保留占用还需原型测量。这是存储与更新时计算换取查询耗时，不是免费的请求缓存。暂不引入全文检索、模糊匹配、共享搜索结果缓存或新排序语义。

## 验证与采用顺序

先做离线原型，比较旧路径与新路径的候选、片段顺序、最终完整 DTO、所有分页和游标；覆盖“学习”、选择性词、空结果、Unicode 展开、占位文字拼接以及链接／媒体／祖先撤回。另验证新旧快照、增量变更、派生行缺失与解析版本升级的回退，以及低权限角色和结果超限行为。

性能对照分别记录准备耗时、存储体量、查询耗时与返回字节，候选和结果必须一致。第一阶段希望同数据下数据库查询中位数至少下降 30%；这是验收目标，未测得收益前不承诺整体秒数。若收益不足，保留原模式，再针对片段算法或剩余正则成本调整，不靠放宽预算获得通过。

这项建议涉及新 SQL 能力、私有派生表和同步接线，需要用户先确认再实现；真实安装、首次准备和生产发布另按任务范围明确授权。它仍是后续建议，本项只实施上述搜索包裹优化，不开始这些写入。

## 验证与用量

两次实际只读会话均严格 TLS，最终 ROLLBACK 并关闭；第一段在同一事务内确认首尾快照一致。客户端实际解密接收约 55 KB，包括计划及函数源码，不含正文。另读少量 Supabase 项目元数据和官方文档，合计为不足 1 MB 的读取量级，未量化底层流量或平台计费。连接器列出的旧项目与当前数据库不符，因此未在那里执行 SQL；实际使用现行数据库配置。本机最初一次 DNS 解析失败时尚未连接或提交 SQL，修正执行权限后完成。

新增包裹对照只返回计划和身份／版本元数据，客户端解密接收约 19 KB，最终 ROLLBACK 并关闭连接；没有下载真实正文。累计本项直接读取仍不足 1 MB 量级，不代表平台账单。
