# 进度记录

每项工作一个文件，随该项工作的合并请求一起提交。2026-10-12 及之前的记录在存档 [PROGRESS.md](../PROGRESS.md) 里，那个文件不再追加，也不往里加“见某个新文件”的链接。

## 怎么写

- 文件名 `YYYY-MM-DD-简短英文名.md`：日期取完成当天，名字用小写字母、数字和连字符，一般就是分支名去掉前缀，例如分支 `fix/play-time-rounding` 写成 `2026-10-12-play-time-rounding.md`。
- 第一行 `# YYYY-MM-DD：标题`，日期与文件名一致，执行者写在标题末尾或正文开头。
- 正文照旧：编辑登记、改了什么、接口与 provider、怎么验证的、限制和下一项。只在演示数据下验证过的要明说。
- 只新建或修改自己这项工作的文件。同一项工作后续有补充，改自己那个文件；别人的记录有出入，在自己的文件里说明，不去改对方的。

## 怎么读

文件名按日期排序，新的在后。开始工作时先看最近的若干条和与手头工作相关的条目，需要更早的背景再到存档里检索。

## 为什么不再写同一个文件

所有合并请求都在 `PROGRESS.md` 顶部加一节，改的是同一个位置。任意两个同时打开的请求，只要其中一个先合并，另一个就在 GitHub 上变成冲突；`.gitattributes` 里“两边都保留”的设置只在本机 git 生效，GitHub 不采用。2026-10-12 一天内因此反复冲突的请求有十多个，没有一个是代码冲突。各写各的文件之后，请求之间和发布请求都不会再因进度记录相撞。

`tests/record-entries.test.ts` 随 `npm run check` 运行：检查这里的文件名与首行格式，拒绝存档里晚于 2026-10-12 的小节，也拒绝存档里指向单独记录的链接。
