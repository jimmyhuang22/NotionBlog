# 2026-11-02：核对 AWS 作品封面的浏览器缓存（Codex）

编辑登记：只新增本记录。用户要求检查缓存是否已启用、是否仍停留在分支，以及刷新作品页为什么仍有加载过程；本轮没有修改应用、缓存策略、运行配置或部署。

## 结论与证据

- 正式作品页的实时 HTML 标记为 `data-public-cache="tagged-v1"`。两张实际封面均返回 `X-Content-Cache-Policy: nb-public-cache-v1`、强 ETag 和 `Cache-Control: private, no-cache, must-revalidate`，说明当前公开缓存及图片重验证路径已启用。
- 两张封面首次有界 GET 分别返回200、60,652及116,166字节；各自携带 ETag 的条件 GET 均返回304、正文0字节。因此协议支持复用原图片字节，但仍须联网确认。条件请求样本约0.46秒，含本机新连接与TLS成本，不代表浏览器单次往返或全站性能。
- 普通刷新后仍为相同缓存模式。浏览器恢复原有分页状态后，前后均为40个相同资产路径、30张实际加载，其余为懒加载。缓存不是靠每次生成新的资产版本失效。
- 原一天免联网策略后来由[公开缓存决定](../decisions/2026-10-21-public-content-cache.md)替换；[10月28日相同现象的记录](../decisions/2026-10-28-image-revalidation-keep.md)明确保留图片逐次验证。[五分钟页面回访](../decisions/2026-10-28-public-cache-revisit-five-minutes.md)针对同一标签页内的站内返回，不覆盖整页刷新。
- 核对时正式 main 仍为 `b9f39fb`。图片响应包装及五分钟 `staleTimes` 实现均已进入该提交的历史，实时响应也与实现相符；不是仅在未发布分支中的功能。Cloudflare 响应仍为DYNAMIC；Vercel专用缓存头不能当作AWS或Cloudflare边缘命中的证据。

## 限制与后续

本轮未取得浏览器 Network 的逐请求缓存命中记录，不声称所有图片在真实刷新时都只返回304。只读浏览器环境不开放 Resource Timing，原生Chrome窗口观察不可用；未改浏览器缓存偏好或安装其他抓取工具。

前后40个资产中，16个完整URL在800档小图与原图之间变化，符合既有封面组件的失败回退路径，但未捕获触发时的HTTP状态。另有界抽查一组小图与原图，当时均返回200，正文分别84,374及896,083字节；不能据此认定回退原因或宣称整个刷新完全免下载。进一步追查应取得当次请求状态，不重复遍历全部图片。

只读范围为作品页打开及一次普通刷新、两张封面的条件验证和一组大小图。独立HTTP检查正文合计1,157,275字节，浏览器图片／后端出口未独立计量，估计总量为数十MB以内；未翻页遍历、批量下载或写数据库。没有SSH登录、清缓存、同步、配置变更或发布。

本项为纯记录，验证记录格式、相对链接、差异和隐私；不重复完整 check／build。若要让刷新后的图片在一段时间内免验证直出，须另行确认浏览器缓存期限及已下载图片的撤回窗口，再实现和发布。
