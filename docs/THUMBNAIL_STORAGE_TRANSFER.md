# 已有小图转存与发布衔接

独立媒体改用 COS 时，原件与 400／800 小图必须在同一目标配置下可读。已有固定集合的 **197 项小图已全部通过 COS 独立 reader 回读核验**，2026-10-15 已由协调者接受最终账、结算预留并精确释放共享锁。原 Supabase 对象和现有运行保留；本次没有切换网站。

## 2026-10-15：固定集合转存完成

197 个不同 SHA 对象共 3,886,392 B，剩余与待查均为 0。最后一轮在获准启动期限内启动，80.358 秒完成：原待查对象首读即通过，其余六项各一次不可覆盖 PUT 和独立 reader GET，无补传。本轮 15 次请求，上传 131,340 B、响应 184,832 B；历史累计 613 次请求、上传 5,059,164 B、响应 5,082,030 B，合 10,141,194 B，低于已明确修订的累计 723 次／15 MiB 上限。

协调者离线核对原始文件索引、冻结代码与实际授权、串行运输指标、190 项旧证明保留及 7 项新增证明；接受最终原字节账，关闭执行授权，释放未用的 30 次请求／1,780,980 B 窗口预留。原 600 次上限及其修订、各次失败和旧账保持历史原件，不重置费用。累计剩余额度不是新的执行许可；原准备清单的未授权标记也不回写成执行回执。

完成范围是这 197 项固定缓存小图的目标对象字节证明。当前账 `cosFullSetReady=true`，`publicationScopeVerified=false`；它不证明新发布批次的父资产资格、小图登记、全部栏目封面覆盖、网站媒体显示或地区性能。下一步由唯一首次完整发布拥有方消费同次 accepted 工件，选择仍匹配父身份、所有者和原件 SHA 的已有小图，再沿现有登记、独立媒体与代表访客流程验收。详见[最终核账记录](progress/2026-10-15-cos-fixed-thumbnails-complete.md)。

## 已准备的固定集合

197 项已验证缓存对应197个不同 SHA 对象：196项400px、一项800px，共3,886,392B。189个已有本机 WebP 以独立文件副本复用，另外8个从已知 Supabase 对象读取，合125,402B。仅使用独立 reader 的固定名单，实际2次 Auth、8次 Storage GET；Auth 响应3,109B，小图响应125,402B，没有来源、SQL、原图、编码或上传。

本地副本全部按既有媒体描述核验长度、WebP 签名与 SHA；不重新生成配方或改尺寸。私有清单记录旧父资产、父原件摘要、所有者、档位、完整小图描述与本地 SHA 文件位置。已核对退役回执的原件摘要：本集合没有命中退役原件；命中共用保护原件的候选继续保留。摘要交叉核对不替代最终发布资格。

固定清单是历史缓存的交付候选，不证明197项全部属于新全课程基线；实际转存另外取得明确批准。原件备份、既有云对象、thumbnail state、缓存和运行回执均保留；新本地副本与输出使用独立私有目录，不覆盖正在接续的旧小图状态。

## 早期真实转存结果（历史）

以下保留早期 47 项回执及当时额度；后续执行、累计上限修订和最终结果以上方 2026-10-15 核账为准，不使用这些历史数字继续派发请求。

用户明确批准固定197项向已验证的上海 COS 私有目标转存，并由独立 reader 回读；初次窗口20分钟，之后另获明确批准延长20分钟。全部尝试仍共享15MiB文件体和600次请求，没有重置计数。虚构样本验收、固定小图转存与首次完整发布分别记录，不扩大为原件迁移、来源读取、SQL登记或网站切换。

首轮第一项22,506B WebP 的三次不可变 PUT 均未收到确认响应；随后独立 reader GET 返回200，实际字节核验通过。续办刷新同一域名的地址与证书核对，跳过已经成功的对象，最多8并发。只有经过证书验证、请求体已发送而响应丢失的 PUT，才允许沿独立 reader 的完整字节核验恢复成功；回读不符或未找到对象不计为成功。对未确认对象先回读；明确返回 `NoSuchKey` 后，只做有界不可变重试。

该阶段最终47个不同对象通过独立 reader 的 SHA、长度与 WebP 格式核验，共881,528B；当时剩余150项共3,004,864B，其中存在尚未确认的写入，不能一律当作未上传。跨会话合并回执后，累计218次保守请求尝试，PUT请求体1,774,454B、响应1,772,384B，合3,546,838B。此前126次／2,131,234B只计本会话，漏计另一执行者的92次／1,415,604B；成功集合重叠，去重后仍为47项，不能相加。续办每次保留获准截止时刻，该时间窗口随后结束。来源、原图、重新编码、SQL及删除均为零。

当时集合 `cosDestinationVerified=false`、`publicationScopeVerified=false`，单独的成功对象清单绑定47项实际回读证据；原本地准备清单、批准凭据和各阶段失败回执保留。当时剩余额度382次请求、12,181,802B；后续改由唯一执行者消费跨会话累计账本，并另行取得有界执行批准。未收到确认的 PUT 始终先由独立 reader 核对实际存储状态，不直接覆盖或猜测失败。

## 转存前的核对

1. 由存储拥有方消费最终合并的 COS 适配（当前见 PR230（旧库 PR #230，记录保留私有））及获准目标、reader／writer、前缀和额度。旧图床、Supabase 原对象与桶权限保持。建桶与虚构样本验收不等同于已经批准整个真实小图集合转存。
2. 使用私有清单与本地文件。每次上传前读取固定 SHA 文件并重新核验实际字节；不依据缓存 URL 重新编码。相同对象键只接受字节完全一致的复用，不覆盖或删除旧对象。
3. 逐对象在目标完成不可变写入和独立 reader 回读，记录实际数量、摘要、字节和失败。本地 `locallyByteVerified` 不能冒充 `cosDestinationVerified`。只准备了 writer 的成功响应也不能代替 reader 验证。
4. 在同次首次完整发布的接受工件中核对父 `assetId / ownerPageId / sha256`，按真实正文引用和当前资格选择可用档位。不同原件字节或被撤回的父资产不能继承旧小图。来源范围和媒体描述不能根据历史缓存补造。
5. 用 [持久小图 reader](PUBLISHED_THUMBNAILS.md)核对实际匹配。该 SQL 扩展可以复用父身份、原件摘要和所有者一致的历史小图，不因新 run 或 policy epoch 一律重新登记。确需新登记时使用专用 published registrar、当前 revision 与已验证目标对象；不调用旧 qualified 接续器去重新读取 Notion。
6. 在网站选择 COS 前确认该版本所需对象完整。用匹配发布版本的原图、400／800代表请求验证独立交付和撤回，访客 Notion 请求应为零。缺少某档小图时，现有入口可读取同一已发布独立原件；坏索引、对象缺失、权限或字节错误明确失败。

维护窗口仍由主运行器拥有方统一协调。旧流程的 publisher 和后续小图步骤都退出后，才暂停新触发、切政策和交接唯一 writer；本轮不会暂停或改写它们。真实迁移、full → seal → initialize、网站模式和调度按具体授权执行。

## 容量和传输口径

本集合独立文件3,886,392B。全部新对象的一次上传加一次完整回读是7,772,784B；若每个 PUT 都遇到既存对象，适配内部冲突核验还可能多读3,886,392B，合11,659,176B，另有桶状态控制响应与请求开销。这里是固定成功路径的文件体口径，不包含重试、请求／TLS头部、后续增长、其他原件和访客出站，不是计费上限。

本轮批准和实际消耗见上方结果。后续预算按运输、剩余集合及失败续办方式确定，不能把本轮批准当作无限重试额度。原准备阶段的未授权标记保留为历史证据，另用明确批准与真实回执记录执行；集合验证和发布资格只在对应阶段全部通过后标记成功，未知额度不使用工程默认值顶替。

历史原件／压缩候选的规划与退役排除见 [媒体迁移预检](MEDIA_MIGRATION_PREFLIGHT.md)。该图库清单和本小图集合都不替代首次全课程的完整媒体集合。

## 本次复盘与后续批次

本次约 3.9 MB 的集合经历了多次执行窗口、补传规则调整和人工跨机交接，协调成本明显偏高。后续应在执行前把整批恢复规则、请求／字节／时间预算和唯一执行点准备完整，减少同一范围内反复审批和重做准备。这些经验用于制定后续方案，不自动修改已批准的额度或重新打开已关闭窗口。

- **尽早验证实际执行环境。** 公网连通、桶根地址返回 403 或本机测试通过，都不能证明固定目标的真实上传与独立回读可用。先在获准的最小样本内验证 reader／writer 的完整路径，再确定整批执行点；目前证据不足以把此前超时归因于某台电脑、某条网络或 COS 服务端。
- **按整批最坏路径准备预算。** 小图字节很少，耗时仍可能由握手和等待响应主导。方案同时覆盖普通上传、既存冲突核验、丢失确认后的独立 GET、严格补传和证明预留；起步保持可核账的串行执行。所有执行者与窗口共用权威累计账，失败和未知响应也计入，测试目录或电脑变化不重置费用。
- **超时先查实际对象。** PUT 未收到确认不能直接判成未写入；本次最后的待查图在新窗口首读即成功。依完整 TLS／发送指标分类，只由独立 reader 的 MIME、长度和 SHA 证明成功；一次 404 只描述当次读取结果。补传保持不可覆盖、单对象有界，权限、证书、未知计量或错误字节仍停止。
- **在方案中隔离反复失败的对象。** 预先规定待查回读、其余健康对象和故障对象新写入的顺序，保留已获得的证明。曾经耗尽恢复次数的对象，下一窗口的新尝试须明确披露；不能通过自动换窗口、改名或清空次数绕过停止条件。
- **先就绪，再签发短时启动凭证。** 输入、冻结代码、运行时、角色配置和传输方式先验收，执行端确认能立即接收后才开始启动有效期。统一记录 UTC 与执行端当地时间，实际运行 T0 由执行端启动时产生。候选、原始回执和路径映射按 SHA 交接；原文件摘要与规范 JSON 摘要分开，接收端不重排原件。过期未启动先交回零请求证据，再处理续签。
- **用结果说明进度。** 每次更新首先给出远端已证明／剩余／待查数、累计消耗、停止原因、下一负责人和动作；离线测试数量放在验证说明里。缓存就绪、目标对象已证明、同批次发布资格与网站显示分别记录，不能用其中一个宣称全部完成。

本阶段收尾依据是最终账已接受、待查为零、预留已结算、共享锁精确释放，以及下游实际接收回执。原清单、缓存图、冻结代码与历史账仍供首次完整发布核验，留在忽略目录；文档合并后仅清理本项已合并分支，材料清理另按下游引用关系处理。
