# 本机遗留锁的只读诊断

这个工具只提供明确指定目录的匿名文件快照。它不查数据库、不连接来源，也不判断任务、提交或预算是否已经收尾。真实运行目录的检查和处置仍须按原拥有方的授权边界执行；本次源码交付没有进行这些操作。

在具备同版源码和 Node 的运行包中，显式指定一个已有目录：

```sh
node scripts/notion-sync/lock-diagnostics.ts --directory /absolute/private/root
```

仅检查 `worker.lock` 与 `manual-run.lock`，不递归。它不读取 `.env`、配置、报告或其他锁；也不创建缺失目录、写回文件、调整权限、发终止信号、调用 unlock 或启动业务。

## 如何理解结果

固定版本 JSON 不含路径、PID、runId、正文或原异常。`reviewRequired` 为 true 时退出码为 2；安全目录的两把锁均缺失时退出码为 0；参数不合法时固定错误、退出码为 1。两把锁均缺失也不证明业务健康或任务已停止。

| 结果 | 含义与处理 |
| --- | --- |
| 缺失目录 | 不创建目录；核对目标与原运行图，不能据此开始任务 |
| 空文件／损坏 JSON／非法 owner | 可能在独占创建后写入前退出，或文件本身损坏；原文件保留，不能由解析失败推定可删除 |
| 已知格式 | 只识别已知 writer 的字段结构；不证明当前进程或任务身份 |
| 未知格式 | 不猜测来源、时间或 owner，不查询其中未被认可的 PID |
| PID 存在 | 只证明该 PID 当时存在，可能已被复用；身份保持未证实 |
| PID 不存在 | 仅一次 ESRCH 观察；子进程、数据库租约和未知提交仍可能存在 |
| 权限未知／读取失败 | 不把无法证明安全当成锁缺失；保留并审阅 |
| 不安全／超限／检查期间变化 | 停止该文件的推断；不修权限、不重试抢占 |

读取限制为每文件 8 KiB，加一个超限探测字节；目录必须是私有、归当前 UID 所有且无符号链接的规范路径。文件也须是私有普通文件；打开使用 O_NOFOLLOW／O_NONBLOCK，避免符号链接和 FIFO 挂起。前后复核目录、文件身份和元数据，但同 UID 写入者的 ABA 替换与最后检查后的变化仍不能彻底排除。结果不能作为后续删除的原子凭据。

## 人工审阅与原有恢复边界

1. 由原运行拥有方确认任务、调度、同版运行包、原始锁和当前授权账本；同名文件可能被不同受控流程占用。
2. 单独核对可信收尾、子进程、数据库租约／未知提交、当前发布和预算。诊断输出没有完成这些核对，也不扩大原授权。
3. 如确需处置，再准备绑定实际文件前后像、唯一拥有方、停止条件和回退的具体方案。空锁、坏锁和未知格式没有自动处理路径；不要从本说明拼出通用删除脚本。

现有 `unlock-stale` 仅保留原 `worker.lock` 显式恢复能力：合法旧 PID 兼容，只在 PID 确认不存在且原文件身份检查通过后移除。PID 存在保持 BUSY；空／损坏／非法 owner 返回 MISCONFIGURED，原文件保留。它不是提交收尾证明，也不处理 manual-run.lock。本项没有为任何实际目录调用这个命令。

完整基线 CLI 的重复 SIGTERM／SIGINT 会持续触发幂等取消，并在原清理结束后移除监听。该修复降低正常取消中的遗留锁风险；SIGKILL、断电、文件系统故障和不合作的外部进程仍有人工审阅边界，不能据此承诺永不遗留锁。

批准与离线验证边界见 [B06 方案](BACKEND_LEGACY_LOCK_DIAGNOSTICS_PLAN.md)和[决定](decisions/2026-10-25-legacy-lock-diagnostics.md)。
