# 部署优化方案：profile 适配与应用版本选择

状态：2026-11-14 第一项已获准本机源码实现、回归及合入 develop，实施见[记录](progress/2026-11-14-published-private-profile.md)，不合 main、不部署。第二项仍仅为待核对设计，明确先不实施；私人接收器和线上配置未变。下文保留两项方案，上海字段和路径角色仍为设计，不是已经存在的生产配置。

## 一、把现役 profile 适配正式纳入源码

**问题与目标。** `scripts/self-hosted/profile.cjs` 原版只接受 qualified 发布模式，现役另有 published/private-disk/display-only 的受限适配。每次复制纯源码都要保留该差异。目标是源码直接支持已使用的受限组合，让正式 release 不再依赖手工补丁；不改变运行配置或扩大内容公开权限。

**拟改范围。** 仅 profile 校验、相关合成回归测试和部署说明。将现役分支整理成明确谓词：public-website、数据库 v2、published、scoped 读取、数据库页面 legacy、媒体 storage/display-only、原图与缩略图 private-disk、独立 self-hosted 媒体入口关闭、共享内容缓存关闭。scoped 和 legacy 显式固定为当前需要的组合；不借本项开放 published+compact 或其他未使用组合。原有 qualified 路径行为保持。

**继续执行的约束。** 配置文件权限／所有者／大小、未知字段拒绝、只读数据库身份、TLS、媒体目录隔离、社交媒体与统计配置检查均继续生效。profile 接受一种模式不等于授予内容资格；reader 的父链、发布范围和撤回校验不变。保留原统计解析，不复制真实配置、密钥或私有内容到测试。

**实施与验证。** 获准后先对照届时最新现役适配，若超出上述组合则报告差异。以本机现有副本准备合成正例、逐条件反例和 qualified 原行为回归，再测专用 build/start 实际入口、禁外连和产物隐私。集中运行一次 Node 24 check/build，向 develop 提独立 PR。代码合入不安装到主机；另获发布授权后，在候选 release 使用正式源码替代旧补丁，通过 profile 兼容和每站基本验收即可，外观未变不要求八项视觉全量。

**失败与估时。** 本机实现、回归及 PR 预计半个工作日，CI 排队另计；不承诺仅复制几行即可完成。线上安装另排窗口，失败恢复上一份已验收 release，不通过改配置、放宽校验修复。旧 release 保留其原适配，新旧比较明确记录。

## 二、将上海应用版本选择从接收器代码中独立出来

**问题与目标。** 本机交接记录显示，接收器把应用 RELEASE 路径写在代码中；只换当前容器，后续自然内容交付仍可能选旧版本。建议只抽出应用选择，保留接收器其他行为。此项最终需要一次明确批准的接收器安装，不能称为“完全不动私人程序”；当前仅准备方案。

**建议设计：受保护的应用选择文件。** 在既有主机管理配置区域放一个普通 JSON 文件，拟含 `version: 1` 与 `release: "<release-name>"`。只存 release 标识，不存凭据、内容版本、来源 buildId 或媒体位置。接收器只读它，部署流程负责更新；不增加守护进程、调度器、下载器或远程配置服务。相比可随意指向任意目录的软链接，这一结构可明确验证版本和路径。

| 部分 | 拟定行为 |
| --- | --- |
| 选择文件 | 单个普通文件，0600，安装时确定并验证可信所有者；拒绝软链接、额外硬链接、超长、未知字段、畸形 JSON 及相对路径穿越。实际目录／账号留在私人安装方案 |
| release 定位 | 只允许固定 releases 根内的单层标识，解析后仍须位于可信根；拒绝越界／可变链接与不存在目录。部署完成的 release 不原地改写，核对提交、BUILD_ID、构建标记和专用入口可读 |
| 交付过程 | 取得既有交付锁后读取一次、验证并固定该次选择；应用指针变化与内容容器替换使用相同既有互斥机制和锁顺序，不新增或重置真实锁、计数 |
| 来源守卫 | 继续验证实际内容导出源的 build/profile；不改成新网站 BUILD_ID，不取消校验，不把应用版本与内容批次混为一谈 |
| 配置继承 | 从届时最新活动内容／运行配置生成新容器，保留来源校验、统计 sidecar 合并、认证、调度及其他已完成修正；不复制旧 active/config 快照 |
| 更新选择 | 先验证新 release，在同目录写临时文件并同步，再原子替换选择文件、同步目录；在既有锁内协调容器切换。记录旧选择和结果，拒绝覆盖与预期不同的新状态 |
| 异常 | 指针缺失／损坏／目标不可读时，在移除当前健康容器前失败；不猜最新版、不从网络补装、不静默降级到写死旧路径 |

**一次性接入顺序（需另批安装）。** 先以实机最新接收器作基线审查补丁；持既有锁，先生成指向当前应用的选择文件，再安装“只替换 RELEASE 来源”的适配。两个步骤中的当前应用都不变，先验证既有容器和配置正常，再等一次自然交付确认仍运行同版本。没有选择文件时不安装新适配，不依赖长期隐式回退。这里不部署新网站版本，便于单独判断接入是否正确。

**以后网站发布。** 验证新产物 → 持既有锁核对当前状态 → 原子更新应用选择并切换当前应用容器 → 每站基本验收 → 异步等自然交付持久性验收。未来不再每次修改接收器源码，但选择文件更新仍属于获准的网站部署操作。

**回退与中断恢复。** 应用切换失败时，在同一互斥约束下恢复旧应用选择，用最新内容配置恢复应用；不回滚数据库、媒体或活动内容批次。文件更新与 Docker 操作不是同一个原子事务，必须记录两阶段状态：指针已改但容器未切、容器已切但回执丢失时先检查实际挂载与指针，再决定完成或回退，不能盲目重放。首次接入失败可在确认接收器没有其他并发修正后恢复本次基线版本；若已出现其他修正，只撤本项差异，不能覆盖全文。

**离线验收与估时。** 先做合成文件系统／容器命令替身：覆盖合法选择、损坏／缺失指针、权限／路径越界、未完成产物、并发发布与交付、两阶段中断、应用回退而内容仍前进、来源守卫及统计配置保留。不得调用真实接收器、锁、计数、Docker 生产容器或采集。原型、测试与差异审查预计 1 个工作日；届时依据实际接收器复杂度调整。一次性安装估计 20–40 分钟，另等自然交付，仅作为待批准安排。

## 建议的批准边界

第一项本机源码、测试及 develop 合并已获批准，正式发布仍未批准。第二项明确先不实施，未来可先单独批准离线原型和测试，再审核一次性接入；不能从第一项批准推导接收器修改授权。任何批准若只针对本机工作，不包含 SSH、主机配置、私人程序安装、业务写入或手动交付。实施前仍须检查最新源码和本机交接，当前记录不当作在线状态证明。
