# 生产部署与交接

最后核对：2026-11-14。此页是正式部署的统一入口；历史记录保留原结论，但不再作为当前目标或操作授权。服务器地址、凭据、受保护配置路径和真实样本保存在忽略的私人交接。

## 当前目标与边界

- **正式博客采用国内上海、默认海外新加坡 Oracle 分流**，两站分别使用 x86_64 和 ARM64；main 是正式源码来源。Git 合并、构建通过和主机实际安装是三个不同状态，正式发布逐次授权。
- **AWS 旧网站已退役，实例继续运行**。旧站服务已停止并屏蔽，专用 Nginx 入口已停用；程序、历史版本、配置、专用日志与恢复包已按后续授权删除；其他服务、磁盘与公网 IP 未动，仍有资源费用。不能再按旧恢复说明原地恢复，见[清理记录](progress/2026-11-13-aws-blog-files-cleanup.md)。不得因 main 合并自动上传 AWS；保留服务器不等于其内容数据持续与新加坡一致。恢复 AWS 流量、停止实例、删除磁盘或地址都需后续明确授权。
- 正式根域和 www 已配置地域分流，统计后台保持新加坡；NS 迁移有缓存过渡，详见[分流验收与回退](progress/2026-11-13-formal-geo-routing.md)。旧预览公网入口已退役，内容导出仍依赖旧预览的本机服务定义和配置。带 candidate 字样的现役服务承接正式流量。详见[旧预览退役记录](progress/2026-11-13-retire-singapore-preview-hostname.md)。
- 当前数据库页面为 `legacy`，媒体为 `display-only`，存储为 `private-disk`，内容读取为 `published/scoped`，共享内容缓存关闭。不得照搬旧 AWS 的双 legacy、云端媒体、Nginx 端口或凭据。
- 网站 release 与私人采集／游戏／交付程序分开。网站更新不覆盖私人运行修复、不执行采集、不调整调度，也不恢复旧 Mac／东京写入流程。

## 下一次获准发布的顺序

1. 读本页、当前私人交接及用户当次范围，确认本次范围涉及哪些正式节点；核对 main 提交、受检树、各节点现役版本、架构、配置摘要及已验证的回退 release。
2. 先处理已知 profile 兼容差异；按下述预检和复用条件，分别准备对应 Linux 架构的公开网站产物：新加坡 ARM64、上海 x86_64。需要构建时各自在匹配环境执行，不跨架构复制原生依赖。预检失败先停止，不启动长构建或切换。
3. 仅安装网站到独立 release，保留现役配置、数据库、展示媒体、私人同步程序和现有 Tunnel 路由。已有 DNS／TLS／Access／防火墙不随版本发布重设。
4. 获准切换后检查专用启动入口、服务状态和错误日志，再从正式 HTTPS 入口完成下述每站基本验收，并补受影响的渲染等功能检查。共享缓存关闭时，不把 tagged-v1 专属首页预热日志当作必需项。
5. 按下述改动范围选择视觉项目，在实际正式入口验收并保存证据；用户明确要求的项目不能自行省略，其他主机通过记录不能代替。字体切片数量仅为估计，按请求成功和实际显示判断。
6. 失败按当次授权回退并停止；未授权不得补改线上配置再试。普通代码回退不恢复数据库快照或改变采集方向，AWS DNS 回退须另外确认范围。

没有当次发布授权时，只做文档、构建准备或获准的只读检查，不因为此流程存在就执行切换。

## 按改动范围安排发布与验收

先比较候选源码与各站实际版本，再判断是否需要安装。main 前进不等于主机必须立即更新；纯说明、测试或仅影响下一次构建的预检改动，可以随下一次网站更新携带。涉及正在使用的启动路径或运行安全修复时不能按“部署工具”名义推迟必要修复。长期规则见[决定](decisions/2026-11-14-deployment-validation-scope.md)。

| 改动范围 | 验证与上线安排 |
| --- | --- |
| 纯文档、记录 | 格式、链接、差异和隐私检查；不为追齐 Git 版本重启主机 |
| 构建／部署工具、测试 | 验证改动涉及的代码和构建流程；没有现役运行行为变化时可不单独部署，不重做八项视觉 |
| 单个页面或组件 | 部署基本验收，加受影响页面、交互、关联主题与屏幕宽度；不重复无关动画／字体全套 |
| 全局样式、字体、导航或共享布局 | 根据影响扩大到八项视觉清单及桌面／手机宽度；说明真实设备和时序观察限制 |
| 媒体、渲染、路由、权限或运行 profile | 基本验收，加对应图片并发、代码／公式、HTTPS rewrite、负向访问或 profile 组合回归；外观未变不要求全站视觉重做 |
| 内容交付中的应用选择或配置继承 | 加交付互斥、来源守卫与配置保持验证；自然交付后确认应用版本仍正确 |

混合改动取各项并集；影响不明先查清，无法排除共享影响时扩大验证。部署方案写明选择理由、复用结果、当次必验和未覆盖项，不能把没做的项目写成通过。

**每次实际切换的基本验收不省略：**核对各站版本／BUILD_ID、配置模式与回退可用性；目标环境依赖、实际用户／挂载权限及构建内存预检；切换后确认专用入口、健康、重启和错误日志；每站抽查首页、代表性内容页及图片可加载、安全头与 HTTPS 关闭栏目 404。构建产物复用时无需运行未发生的构建，但仍核对依赖与 runtime 读取权限。按实际节点分别验收，不能把 DNS 命中另一站的结果算作本站通过。

自然交付可以后台等待，不要求持续占用浏览器；中途报告“已上线、自然交付持久性待验”，完成后补记。不能因等待时间长主动触发同步，或把交付前健康当成持久性通过。应用版本选择没有随本次改变、且相关行为有适用的通过记录时，不重复无关交付演练。

## 复用通过结果与产物

1. **源码验证**：记录受检提交／树、命令、环境、结果和适用范围；同一版本已完成的 check/build 不在每台主机再跑一遍全套。普通合并若文件树相同，可沿用原结果。随后仅改无关说明时，对照实际差异补格式、链接、隐私检查；应用代码、依赖、契约、fixtures、协议、构建／测试配置或相关运行输入变化则重验受影响范围，不能沿用旧版本的全绿结论。
2. **平台结果**：本机、平台、目标机和线上结果分开记录。发布 PR 仍遵守完整集成版本的平台要求；不关闭工作流、改保护规则或把 SKIPPED 当通过。已有成功运行需与候选版本及检查环境对应，失败／中断记录保留；Vercel 账号封锁与 GitHub Actions 分开判断。
3. **依赖与产物**：锁文件未变时优先复用各站已验收依赖，并执行预检；ARM64 与 x86_64 的原生依赖、产物分别准备。只有源码／构建输入、profile 适配、Node 与目标 Linux 架构／ABI 等均匹配、启动标记和产物检查有效时才复用产物。不能把旧包重写版本号冒充新构建，不能用 macOS 或另一架构的构建成功替代目标产物验证。复用依赖不等于复用整个构建。
4. **实际运行适配**：现役额外补丁不包含在纯 main 的检查结果中，须单独列出差异并验证；未知差异先停。主机 UID、挂载、内存和当前内容会变化，历史通过不代替切换当次检查。已有产物的启动和配置兼容仍需确认。

两站可在资源和当次授权允许时并行准备产物，切换保持先新加坡验收、再上海。只传必要源码差异和依赖补充，不为省时间修改现役依赖或跨架构整包复制。预检失败不自动放宽权限或扩容；失败回退及停止按当次批准执行，不回滚内容数据。

后续工程方案与分项状态见 [profile 与应用版本选择优化](DEPLOYMENT_OPTIMIZATION_PROPOSAL.md)。profile 只获准本机源码工作；上海应用选择仍待批准，未安装接收器，也没有线上授权。

## 构建与切换前预检

保持两站现有架构，不因一次构建失败迁移系统。预检脚本 `scripts/self-hosted/preflight.ts` 不安装依赖、不读取真实配置、不联网、不启动私人程序。以下是后续获准部署时的步骤，不表示本机修改已安装到主机。

1. **两份依赖均须完整**：核对根目录和 `scripts/game-sync` 的 package.json 与各自 lockfile，检查适用架构的非 optional 包及已存在 optional 包的锁定版本，并确认构建关键入口和声明文件可读。`psn-api` 即使不作为网站任务运行，仍被全工程类型检查引用；只复用根 node_modules 不够。缺少包时在独立新 release 按原锁准备依赖，游戏依赖安装沿用 `--ignore-scripts`；不复制或运行私人同步根。预检只核元数据／必要入口，不替代完整性校验和实际构建。
2. **以实际账号检查权限**：先在新 release 内、实际构建用户及实际挂载方式下运行 build 预检。检查祖先目录可穿越、已有 `.next` 树及 TypeScript 输出可写，并在根与已有 `.next` 创建后立即删除临时探针目录。合法的 release 内 Next 软链接可保留，悬空或指向 release 外的输出链接拒绝；不自动 chmod/chown，不放宽家目录或现役目录。构建后在网站运行用户与只读挂载下运行 runtime 预检，核对产物、静态文件及专用入口可读；root 构建通过不能替代运行账号检查。runtime 预检不创建探针，也不代替启动标记／健康验收。
3. **在实际构建容器／服务限制内测内存**：Linux 同时读取 MemAvailable、Node 可用内存与 cgroup 约束；不能只看宿主机总内存或 `--max-old-space-size`。本次经验设为起始门槛：有效内存容量至少 1280 MiB、进程当前可用至少 1024 MiB、宿主当前可用至少 1280 MiB（为其他服务留至少 256 MiB 的预算余量）。SwapFree 单列，不加进 RAM 凑门槛。读不到、低于门槛即停止；不自动扩容、加 swap、重启服务或改变容器限制。门槛不是峰值保证，后续仍观察构建耗时、内存压力与 OOM；线上负载更高时应留更大余量。macOS 本机验证会明确标成 Linux 内存未验证，不能据此批准目标机切换。

下面命令须分别由实际构建用户、实际网站运行用户在待发布目录内执行；将 UID 和架构替换成部署方案中的值（`x64` 是 Node 对 x86_64 的名称）。容器内检查须采用计划中的用户、挂载和内存限制，并禁止拉取镜像与联网。无需为检查授予新权限。

```sh
node scripts/self-hosted/preflight.ts --stage build --uid 10001 --arch x64
npm run build:self-hosted -- --public-website
# 以上构建通过后，以网站运行用户、最终只读挂载检查：
node scripts/self-hosted/preflight.ts --stage runtime --uid 10001 --arch x64
```

专用 build 入口在 Next 开始前自动执行依赖、目录和 Linux 内存检查，防止漏跑；显式命令另核对预期 UID／架构。检查失败不会自动修复或重试。普通本机离线 `npm run check/build` 不因此连接主机，仍与部署分离。
