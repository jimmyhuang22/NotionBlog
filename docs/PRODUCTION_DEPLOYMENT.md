## 空间、性能与内容交付

- 排查空间或超时时，先找占用最大的表、文件或查询，问清这些数据中哪些供访客读取、哪些只供采集或恢复。若按保留规则一项也清不了，说明规则服务什么目的、是否适用于展示库，再决定清理、扩容或调整拓扑。
- 发包前按访客可读结果核对源快照：已发布读者版本、可见页面及正文摘要、可展示媒体及其所属页面、公开栏目数据与有效访问权限。能影响页面或图片公开范围的撤回、隐藏和权限变化须体现在比较中。仅缓存事件或内部采集历史变化时，复用已核验的交付包。包体 SHA 仍用于确认实际收到的文件完整。
- 同一轮复用已经验证的上海媒体基线和 Mac 回退档。批次、目录内容或归档文件发生变化，或出现损坏迹象时，只复验受影响项。恢复格式、接收器及恢复输入等价时复用已通过的空库恢复演练；实际换库后仍检查线上结果。
- 交接正文只写上线结论、异常及其影响；有未决事项时写清下一步。逐项通过记录留在原回执，按需链接。

日常自然交付已在新加坡上传和上海下载两端接入预算执行器。每批每程各限 200 MB（十进制），含首传和一次完整重传。发起传输前校验包大小，按整包字节数持久预记每次尝试。任一程预计超限时停止该批并先取得授权。单次授权另有更低上限时依该次上限。见[预算执行与验收记录](progress/2026-11-22-collection-retention-rehearsal.md)。

采集队列中可证明事务已经回滚、未产生下游提交的记录，可沿原队列重入，复用操作标识并核对来源权限。已提交时对账并结案，结果不明或来源已变化时保留复查。两站同批签收用来确认本次交付完成，依照 AGENTS.md，开工时可直接按提交号、现役指针与可用证据推进。

1. 读本页、当前私人交接及用户当次范围，确认本次范围涉及哪些正式节点；核对 main 提交、受检树、各节点现役版本、架构、配置摘要及已验证的回退 release。
2. 先处理已知 profile 兼容差异；按下述预检和复用条件，分别准备对应 Linux 架构的公开网站产物：新加坡 ARM64、上海 x86_64。需要构建时各自在匹配环境执行，不跨架构复制原生依赖。预检失败先停止，不启动长构建或切换。
3. 仅安装网站到独立 release，保留现役配置、数据库、展示媒体、私人同步程序和现有 Tunnel 路由。已有 DNS／TLS／Access／防火墙不随版本发布重设。
4. 获准切换后检查专用启动入口、服务状态和错误日志，再从正式 HTTPS 入口完成下述每站基本验收，并补受影响的渲染等功能检查。上海切换应用后同时做一次[接收器的现役容器核对](#上海接收器的现役容器核对)。共享缓存关闭时，不把 tagged-v1 专属首页预热日志当作必需项。
5. 按下述改动范围选择视觉项目，在实际正式入口验收并保存证据。日常由 Mac mini 按[上海站浏览器验收](#上海站浏览器验收)复验；涉及换库时按[单库替换顺序](#上海单库替换与恢复)执行。用户当次指定的检查都要完成，验收记录须对应实际命中的主机。字体切片按请求是否成功和实际显示判断。
6. 线上验收发现问题时，按[生产回退原则](#生产回退原则)处理并记录结果。
7. 本次范围内各站验收通过后，逐站执行[退役清理](#验收后的退役清理)，记录释放空间、剩余空间及下次交付是否放得下。

没有当次发布授权时，只做文档、构建准备或获准的只读检查，不因为此流程存在就执行切换。

## 生产回退原则

- **立即回退。** 触发条件限于站点不可用、核心功能故障、数据风险或权限风险。触发时停止后续切换，按当次授权将受影响站点立即切回已验收版本。回退后核对实际版本、健康及基本验收结果。
- **轻微展示问题留到下一版。** 站点可用、核心功能正常，且问题仅影响展示时，保留线上版本。把现象和影响范围作为已知问题记入交接，修好后随下一次发布一起上线。
- **先确认真实影响。** 验收脚本报错或单条检查链路超时时，先核实生产现场。其他未达到立即回退门槛的问题按实际影响和当次安排处理。

应用回退只切换应用版本。线上配置变更、数据库恢复和采集方向调整按各自授权处理。[回退原则决定](decisions/2026-11-19-production-rollback-policy.md)

## 按改动范围安排发布与验收

先比较候选源码与各站实际版本，再判断是否需要安装。main 前进不等于主机必须立即更新；纯说明、测试或仅影响下一次构建的预检改动，可以随下一次网站更新携带。涉及正在使用的启动路径或运行安全修复时不能按“部署工具”名义推迟必要修复。长期规则见[决定](decisions/2026-11-14-deployment-validation-scope.md)。

| 改动范围 | 验证与上线安排 |
| --- | --- |
| 纯文档、记录 | 格式、链接、差异和隐私检查；不为追齐 Git 版本重启主机 |
| 构建／部署工具、测试 | 验证改动涉及的代码和构建流程；没有现役运行行为变化时可不单独部署，不重做八项视觉 |
| 单个页面或组件 | 部署基本验收，加受影响页面、交互、关联主题与屏幕宽度；不重复无关动画／字体全套 |
| 全局样式、字体、导航或共享布局 | 根据影响扩大到八项视觉清单及桌面／手机宽度；说明真实设备和时序观察限制 |
| 媒体、渲染、路由、权限或运行 profile | 基本验收，加对应图片并发、代码／公式、HTTPS rewrite、负向访问或 profile 组合回归；外观未变不要求全站视觉重做 |
| 内容交付中的应用选择或配置继承 | 加交付互斥、来源守卫与配置保持验证；自然交付后确认应用版本仍正确 |

混合改动取各项并集；影响不明先查清，无法排除共享影响时扩大验证。部署方案写明选择理由、复用结果、当次必验和未覆盖项，不能把没做的项目写成通过。

**每次实际切换的基本验收不省略：**核对各站版本／BUILD_ID、配置模式与回退可用性；目标环境依赖、实际用户／挂载权限及构建内存预检；切换后确认专用入口、健康、重启和错误日志；每站抽查首页、代表性内容页及图片可加载、安全头与 HTTPS 关闭栏目 404。构建产物复用时无需运行未发生的构建，但仍核对依赖与 runtime 读取权限。按实际节点分别验收，不能把 DNS 命中另一站的结果算作本站通过。

自然交付可以后台等待，不要求持续占用浏览器；中途报告“已上线、自然交付持久性待验”，完成后补记。不能因等待时间长主动触发同步，或把交付前健康当成持久性通过。应用版本选择没有随本次改变、且相关行为有适用的通过记录时，不重复无关交付演练。

## 上海单库替换与恢复

上海博客机运行一套现役业务库。换库前的数据库与媒体回退归档只长期保存在 Mac mini。应用保留或重建仍按指定回退版本处理。Mac mini 负责日常隔离恢复和外部浏览器验收；恢复流程变更时，才在上海备用机按博客机架构与资源约束演练。

1. 新加坡先验最终应用和迁移后的数据，核对发布批次、读者权限、功能与媒体。上海可以预先备齐并校验同批输入，单库替换须等新加坡通过。
2. 上海停站前，在 Mac mini 保存与上海现役版本对应的完整归档，包括数据库、媒体、恢复所需的角色与授权信息，记下应用提交、构建身份和对应的运行配置。现役接收器核对父批回退档的实还原记录，同一归档沿用已有结果。若要取消逐批要求，先证明旧批精简库、同代媒体和读者权限可从冻结输入重现；切回时还须遵守其后生效的撤回。恢复输入缺失或格式、权限、接收器改变时进行实还原。在新归档验好之前保留上一次已验证归档。确认存档所在磁盘已挂载、Mac 可用、能连接上海，上海工作盘够放候选、恢复临时输入、索引和 WAL。
3. 上海进入维护，沿用发布与内容接收的互斥，记录旧版本，在单库位置装入候选。博客机自检同批数据、实际读者与权限、应用构建、健康接口、首页、分页和图片。通过后开放入口，由 Mac mini 做外部浏览器验收。
4. 换库失败时保持维护，从 Mac mini 经已核验的加密管理连接上传已验旧归档，校验完整摘要后恢复旧库、媒体和对应应用，重复自检及外部验收。按实际情况分别记录等待 Mac、传输、恢复和复验耗时。已使用的服务器端临时副本在恢复验收后清理。日常小展示问题沿用生产回退原则。
5. 恢复流程变更（例如备份格式、数据库大版本、接收器恢复步骤或权限恢复方式变化）时，在备用机隔离运行一次正常替换和失败恢复，记录停站时长、磁盘峰值及清理结果。若该次演练需要在备用机启动浏览器，沿用下方的单次授权与独立清理流程。

### 上海接收器的现役容器核对

上海应用切换后，以接收器的现役记录调用同一套只读容器检查 `Rotation.container(active)`，确认它能识别正在运行的容器。核对容器挂载的应用提交、运行配置、业务库与读者角色，并确认正式入口指向记录中的监听端口。随当次基本验收做一次，在交接简记结果即可。

## 上海站浏览器验收

日常从 Mac mini 浏览器访问正式域名，使用正常公网 DNS、有效 TLS 和新会话，核对实际对端和上海预期 `BUILD_ID`。按本次改动验桌面、手机视口和关键交互。若地域分流命中新加坡，注明实际命中站点；可在保留正式域名和证书校验的情况下另做定向探测，分别记录定向结果与自然访问结果。

### 恢复流程变更时的备用机浏览器操作

1. **先确认站点和版本。** 在轻量云控制台核对私人交接里的上海备用机实例，从该实例的「执行命令」进入腾讯云自动化助手。根据当次发布记录确认正式域名、上海生产对端和预期 `BUILD_ID`。让备用机用正常公网 DNS 与有效 TLS 打开正式域名，核对实际建连对端、健康接口和页面版本。上海通过记录须对应本次上海构建。
2. **临时准备浏览器环境。** 优先使用备用机上可用且保留沙箱的浏览器。需要临时准备时，从官方渠道获取并校验 Chrome Headless Shell，从 Ubuntu 已签名的软件包索引解包所需运行库和字体。拉丁及中文字体、Fontconfig、浏览器资料和验收脚本放在本次临时目录。浏览器以普通用户运行，调试只监听回环。
3. **AppArmor 按次单独授权。** 现有规则无法启动浏览器沙箱、需要临时规则时，加载前单独取得用户对这次验收的明确授权。规则只匹配经校验且由 root 持有的 Chrome 可执行文件的确切路径。浏览器保留自身沙箱。后续验收如需临时规则，重新取得授权。
4. **按当次清单验证页面与交互。** 用新会话检查首访，等文档和相关样式就绪再断言。按范围选择主题和模拟视口，量横向溢出时以页面实际可视宽度为准。图片检查实际加载，外链用真实点击确认新标签页和目标地址。与当次 `BUILD_ID` 一起记录通过项、缺少的测试样本、作业和任务编号及退出码。
5. **清理后另起只读作业复查。** 验收结束或中断后，停止本次浏览器，卸载临时 AppArmor 规则，移除浏览器、依赖、字体、资料和临时目录。另用一次独立云助手作业确认本次规则、浏览器进程、运行目录和下载目录各为 0，并复核正式站健康与当次版本。交接分别记录验收和清理回执。清理结果尚未核实时标记为待确认。

当前分工见[上海单库、归档与验收决定](decisions/2026-11-22-shanghai-single-database-and-mac-recovery.md)。备用机演练信息与真实回执见私人交接。

## 复用通过结果与产物

1. **源码验证**：记录受检提交／树、命令、环境、结果和适用范围；同一版本已完成的 check/build 不在每台主机再跑一遍全套。普通合并若文件树相同，可沿用原结果。随后仅改无关说明时，对照实际差异补格式、链接、隐私检查；应用代码、依赖、契约、fixtures、协议、构建／测试配置或相关运行输入变化则重验受影响范围，不能沿用旧版本的全绿结论。
2. **平台结果**：本机、平台、目标机和线上结果分开记录。发布 PR 仍遵守完整集成版本的平台要求；不关闭工作流、改保护规则或把 SKIPPED 当通过。已有成功运行需与候选版本及检查环境对应，失败／中断记录保留；Vercel 账号封锁与 GitHub Actions 分开判断。
3. **依赖与产物**：锁文件未变时优先复用各站已验收依赖，并执行预检；ARM64 与 x86_64 的原生依赖、产物分别准备。只有源码／构建输入、profile 适配、Node 与目标 Linux 架构／ABI 等均匹配、启动标记和产物检查有效时才复用产物。不能把旧包重写版本号冒充新构建，不能用 macOS 或另一架构的构建成功替代目标产物验证。复用依赖不等于复用整个构建。
4. **实际运行适配**：现役额外补丁不包含在纯 main 的检查结果中，须单独列出差异并验证；未知差异先停。主机 UID、挂载、内存和当前内容会变化，历史通过不代替切换当次检查。已有产物的启动和配置兼容仍需确认。

两站可在资源和当次授权允许时并行准备产物，切换保持先新加坡验收、再上海。只传必要源码差异和依赖补充，不为省时间修改现役依赖或跨架构整包复制。预检失败按前述预检规则停止。切换后的问题按[生产回退原则](#生产回退原则)处理。

上海正式接收器已启用单库替换，按已验收的构建身份启动网站。应用或接收器升级时核对默认应用与正在服务的版本。历史方案见 [profile 与应用版本选择优化](DEPLOYMENT_OPTIMIZATION_PROPOSAL.md)。

## 构建与切换前预检

保持两站现有架构，不因一次构建失败迁移系统。预检脚本 `scripts/self-hosted/preflight.ts` 不安装依赖、不读取真实配置、不联网、不启动私人程序。以下是后续获准部署时的步骤，不表示本机修改已安装到主机。

1. **两份依赖均须完整**：核对根目录和 `scripts/game-sync` 的 package.json 与各自 lockfile，检查适用架构的非 optional 包及已存在 optional 包的锁定版本，并确认构建关键入口和声明文件可读。`psn-api` 即使不作为网站任务运行，仍被全工程类型检查引用；只复用根 node_modules 不够。缺少包时在独立新 release 按原锁准备依赖，游戏依赖安装沿用 `--ignore-scripts`；不复制或运行私人同步根。预检只核元数据／必要入口，不替代完整性校验和实际构建。
2. **以实际账号检查权限**：先在新 release 内、实际构建用户及实际挂载方式下运行 build 预检。检查祖先目录可穿越、已有 `.next` 树及 TypeScript 输出可写，并在根与已有 `.next` 创建后立即删除临时探针目录。合法的 release 内 Next 软链接可保留，悬空或指向 release 外的输出链接拒绝；不自动 chmod/chown，不放宽家目录或现役目录。构建后在网站运行用户与只读挂载下运行 runtime 预检，核对产物、静态文件及专用入口可读；root 构建通过不能替代运行账号检查。runtime 预检不创建探针，也不代替启动标记／健康验收。
3. **在实际构建容器／服务限制内测内存**：Linux 同时读取 MemAvailable、Node 可用内存与 cgroup 约束；不能只看宿主机总内存或 `--max-old-space-size`。本次经验设为起始门槛：有效内存容量至少 1280 MiB、进程当前可用至少 1024 MiB、宿主当前可用至少 1280 MiB（为其他服务留至少 256 MiB 的预算余量）。SwapFree 单列，不加进 RAM 凑门槛。读不到、低于门槛即停止；不自动扩容、加 swap、重启服务或改变容器限制。门槛不是峰值保证，后续仍观察构建耗时、内存压力与 OOM；线上负载更高时应留更大余量。macOS 本机验证会明确标成 Linux 内存未验证，不能据此批准目标机切换。

下面命令须分别由实际构建用户、实际网站运行用户在待发布目录内执行；将 UID 和架构替换成部署方案中的值（`x64` 是 Node 对 x86_64 的名称）。容器内检查须采用计划中的用户、挂载和内存限制，并禁止拉取镜像与联网。无需为检查授予新权限。

```sh
node scripts/self-hosted/preflight.ts --stage build --uid 10001 --arch x64
npm run build:self-hosted -- --public-website
# 以上构建通过后，以网站运行用户、最终只读挂载检查：
node scripts/self-hosted/preflight.ts --stage runtime --uid 10001 --arch x64
```

专用 build 入口在 Next 开始前自动执行依赖、目录和 Linux 内存检查，防止漏跑；显式命令另核对预期 UID／架构。检查失败不会自动修复或重试。普通本机离线 `npm run check/build` 不因此连接主机，仍与部署分离。

## 验收后的退役清理

- 两站按现役应用和指定回退应用保留构建及其依赖。更早的上海应用可用 Mac mini 按对应提交、锁文件和 Linux x86_64 配置重建。核实服务、容器、镜像和待交付作业均未引用后，清走旧应用产物。
- 上海接收器完成签收时自动清掉本批临时包和解包目录。签收记录、仍被引用的分块和媒体按用途保留。中断作业保留续跑材料。
- 交接每站写一句实际释放量、所在磁盘剩余空间，以及能否容纳下一次收包、恢复和索引的峰值。容量不足时写明差额。

## 后续交接要写什么

记录正式主机角色、源码提交与实际差异、BUILD_ID、专用服务／release、配置模式、验证结果与限制，以及本次是否部署或回退。私人材料中另写已有连接流程和真实样本；不在公共文档加入账号、来源 ID、令牌或签名媒体 URL。保留历史 AWS 回执，但加上“历史、不再作为默认部署入口”的指向，避免两条工作线重复发布。


## 作品名地址上线

游戏、书籍和影视需要随同一版本切换。安装及切换按该次正式发布授权执行。

1. 在内容发布主库用现有 owner 安装流程，在单一事务内安装 [作品名地址迁移](../database/library-url-migrations/001_library_urls.sql)。迁移以已发布快照回填名称。需要指定少数既有作品短名称时，安装事务先用参数化 `set_config('nb_library_urls.initial_names', $1, true)` 提供私有 JSON 数组，元素为 `{ "kind": "game", "id": "<内部记录 ID>", "name": "<确认的名称>" }`。在隔离候选库先检查重名及难读名称，确认后再提交正式安装。
2. 将同一份 `nb_library_urls`、`nb_library_urls_api`、名称表数据和关联触发器纳入两地现有内容交付及恢复核对。两地验收候选库中的分配结果和名称读取权限。同步程序后续提交向主库自动分配新增名称。
3. 确认两地候选服务都能以网站只读角色调用名称读取函数，再在两地新版本 profile 同时启用 `DATABASE_LIBRARY_URLS=title`。抽查每类的新详情 GET／HEAD、旧详情 GET／HEAD 404、正文链接、站内搜索和站点地图。旧地址 404 应无跳转目标。确认搜索和站点地图只提供新详情地址。
4. 如需回退，随网站代码和 profile 一起回退。保留主库名称登记，下一次启用沿用相同分配。

## 学习区可读地址上线

1. 在隔离候选库依序验证[学习区名称登记](../database/study-url-migrations/001_study_urls.sql)和[课程编号迁移](../database/study-url-migrations/002_normalize_course_codes.sql)。用真实目录中未经整理的课程编号和标题字段验收，由网站只读角色直接验证预期的短地址、重名和撤回。正式安装按当次批准在新加坡内容主库的 owner 事务内执行。已安装第一份迁移且尚未开放可读地址时，补上第二份迁移，保留已登记的笔记短名。
2. 把主库的 `nb_study_urls`、`nb_study_urls_api`、名称表数据和触发器纳入精简、备份、恢复与上海内容交付。两地须共享同一份分配结果，含仍保留的历史名称。验证增量发布后名称的新增、精简后名称清单的完整及接收端网站角色的读取权限。单独重建名称表会丢失保留记录，应从主库交付该表。
3. 在两地候选 profile 启用 `DATABASE_STUDY_URLS=title`。同批验收学习项目、课程、深层子页、正文链接、课程目录、前后篇、搜索、规范链接和站点地图。对新旧课程和笔记地址抽查 GET／HEAD，新地址返回 200，旧 ID 地址返回 404 且没有跳转。两站沿用既有发布审批安排。
4. 需要回退时，随应用配置恢复地址模式并保留主库名称登记。下次启用使用同一份分配结果。
